## GPU and cores (the owner's first wish)
Done on 2026-11-13 and measured (numbers from `cut-engine/tests/playback.rs`, release, on runs with no other cargo or rustc running; before = the tree of 09:13 the same day, built aside and run alternately with after):
- One GPU for everything: `cut_engine::gpu::pick_adapter` (Direct3D 12 first, then `CUT_ADAPTER`, then the discrete GPU) is used by `Gpu::headless` and by eframe in `cut-app/src/main.rs` (DX12 backend only, NV12/P010/16-bit-norm features from `gpu::device_descriptor`); `Engine::new` makes the `Bridge` and calls `cut_decode::prefer_adapter`, so `Accel::Auto` decoders open on the same adapter. eframe's default here was the GTX 1650 on Vulkan (no sharing possible); the Radeon drives the screen, but compositing there is 3D-bound (88 %) and 3-4x slower, so the GTX 1650 is chosen and the window is presented across.
- Shared frames: hardware decoders on that adapter copy each kept frame into a ring texture opened in wgpu (`share.rs`), plane views with the `decodeYuvUnorm` shader (which turns unorm values back into integer codes), fences around each render. `tests/share.rs`: H.264, HEVC and VP9 give byte-identical renders through both routes; Main 10 (P010) is unproven (no 10-bit encoder here). Any failure falls back to read-back per source (`share_failed`), no bridge falls back to the old route.
- A copy the decoder's driver holds back (Flush is not enough: 50 ms behind a seek) is finished with `Ring::settle` when a render waits for it and before the worker idles.
- Hardware sessions: none of the two GPUs refused a decoder up to 96 (`tests/sessions.rs`); the limit is video memory, so `route.rs` sends a file to software once the process uses 75 % of the adapter's budget. Decoders share at most 4 D3D11 devices a GPU (`d3d.rs DEVICES`).
- Off the UI thread: text clips, graphics, captions and slates (`raster.rs`, one thread an engine; the previous picture shows until the new one is drawn; a render with a 1080p caption on the way takes about 0.6 ms, the one that uploads it 2.6 ms); scopes counts (`Engine::scopes` never waits; each render is counted as submitted while the scopes are open). Thumbnail workers: cores / 4 (2 to 4), waveform workers cores / 8 (1 to 2), held while playing.
- Results, 1080p with Lumetri, frames a second before -> after: 1 layer 249 -> 704, 3 layers 111 -> 262, 6 layers 54.5 -> 129, 4K 48.7 (82 in the other run) -> 193; cores busy 4.8 / 9.1 / 10.4 -> 0.7 / 1.5 / 1.9. Limiter now: NVIDIA Video Decode at 90-98 % (about 790 decoded 1080p frames a second in total, the same at 3 and 6 layers). Seek of three 1080p sources to the whole frame: median 409 -> 92 ms, worst 675 -> 200 ms; to the first picture (the sync sample, shown while decoding on): 7 ms median. Private memory 753 / 1672 / 2729 -> 581 / 892 / 1463 MB. Peaks of a one-hour WAV 2.49 -> 1.41 s (PCM reads no longer decode 12 s of pre-roll a 10 s window; buffers reused).
Left:
- The `\GPU Engine` counters show 0 % 3D for this process on the GTX 1650 in every run, before and after (the Radeon's 3D shows): the compositor's GPU cost there is not measured.
- Memory by stage (`playback.rs memory_by_stage`), 2026-11-16, before -> after, two alternated runs each (identical within 3 MB): the device 287 -> 80 MB private (GPU-visible system memory 88 -> 28 MB), 6 layers played 962 -> 746 MB private and 1205 + 241 -> 1106 + 117 MB of video memory, with the same frames a second (3 / 6 layers and 4K: 264 / 130 / 192 -> 261 / 130 / 191, NVIDIA Video Decode at 91-98 %) and seeks (median 95 -> 93 ms). The cause was wgpu's defaults: a shader-visible descriptor heap of a million descriptors and 64/128 MB memory blocks (`gpu::device_descriptor` now asks for 131072 descriptors and `MemoryHints::MemoryUsage`; the app's device takes the same descriptor). Dropping the 8 extra decoder output textures changed nothing measurable (the NVIDIA H.264 decoder ignores `MF_SA_MINIMUM_OUTPUT_SAMPLE_COUNT`: 1106 MB either way); the request is gone. A 1080p hardware decoder now holds about 90 MB of video memory (its own surfaces; not reducible from here), its 16 shared frames 48 MB, the compositor's pooled pictures about 35 MB a layer. Budgets: shared frames 768 MB of video memory in all, 16 a source; RAM frames 1.5 GB. A source the last render neither drew nor prefetched closes its decoder and lets its frames go after 3 s without work (`media::IDLE_CLOSE`, `tests/idle.rs`), so a paused editor keeps only the decoders of what it shows (before, nothing closed until renders came again).
- Going backwards (`tests/scrub.rs`, 15 rounds each side, three alternated processes): a decoder restarted at a sync sample for a playhead moving back now keeps the frames on the way in its cache (they are the next ones asked for; same 16-frame cap, 47 MB on the GPU either way): stepping back 59 frames one at a time 1.47 s -> 0.19 s in all (each step median 25 ms -> 0.6 ms; a restart every 16 frames still costs one GOP decode, worst 46-118 -> 49-70 ms), scrubbing back 3 frames at a time 1.23 s -> 0.38 s for 50 steps; forward stepping unchanged (159 -> 148 ms for 60). A second decoder decoding the previous GOP ahead of a backward scrub was not built: with the cache kept, what is left is one GOP decode each 16 frames back, and another decoder costs about 90 MB.
- Paused (`scratchpad/play-runs/idle-gpu.ps1`, the demo project open, not playing): the engine renders nothing and no decoder works (2 renders in the first second, then none), the process takes 2.4 % of one core and 0.16 % of a GPU's 3D engine; the window still paints 4 frames a second while paused (the report's `frames`), which is cut-app's.
- Read-ahead is the prefetch window the player sets (2 s, as far as each cache holds); there is no separate read-ahead thread, and decoding is one thread a source. A long file's peaks are not paused mid-file when playback starts.
- Export feeds the encoders from memory, measured and kept (Export below): the encoder that would take the compositor's texture directly (Direct3D 12 on the GTX 1650) spends 3-4 ms a frame inside `ProcessInput` whatever its input, and the fastest one (AMD's) is on the other GPU.
- In the app run (`CUT_PLAY`, demo project, 18 s; `scratchpad/look-windows-2`, `measure.ps1`): the dropped frames at 2.5-2.8 s were one render of 218-267 ms, nearly all of it Direct3D 12 compiling the pipelines the dissolve, the mask and the clip's effects first need (Basic Color Correction 113-153 ms, mask 55-60 ms). `Gpu::warm` now makes every pipeline (`gpu::variants`) on a thread when the monitors start; the report's `program.pipelinesCompiled` (renders that had to compile) is 0 in every run since. Quiet runs, docked: before 39 and 48 dropped, after 1 and 1 (Program in a window: 5-6 -> 0). The stalls of 360-1100 ms inside eframe's paint seen between 1 and 5 s did not come back on 2026-11-16, and the guess (the GPU queue waiting on a decoder copy) is not what the measurement shows: in 3 app runs (traces of each render's waits on copies) a render waited on an unfinished copy 0, 2 and 3 times in 535, 487 and 429 renders, none at a stall; headless (`tests/stalls.rs`: the demo's 720p-then-1080p start in real time at 60 Hz, prefetching 2 s ahead, the GPU drained after each frame) the 1080p decoder opens 2 s ahead on its worker and the worst frame took 4.8 ms of render and 5.7 ms of GPU in 5 runs. What does reproduce the signature (a frame's CPU time in paint as long as the gap) is another process's GPU work: with the playback benchmark running beside the app, paint stalls reached 254 ms and 98 frames dropped in 14 s; with compilers alone, 120 ms. So the stalls seen were most likely other agents' GPU work on the same GTX 1650; nothing in the engine waits there.

## Decoders
Done: Opus (mono, stereo), FLAC, MP3, VP9 (GPU), VP8; on 2026-11-16 (`cut-decode/tests/{alac,flac,opus,inventory}.rs`):
- ALAC in Rust (`cut-decode/src/alac.rs`, after Apple's reference decoder; MP4 `alac` entries and Matroska `A_ALAC` read by cut-formats, which the JavaScript does not): files from Microsoft's ALAC encoder (its output type carries no magic cookie, so the test writes Apple's default config) decode sample-exact, mono and stereo, sweep, silence and full-scale noise (the uncompressed escape); 3000 truncated or bit-flipped frames are errors, never a panic. Unproven: 20/24/32-bit files (the encoder takes 16-bit input only), more than two channels.
- FLAC guard (`cut-decode/src/flac.rs`): Microsoft's decoder gets a stream header rebuilt from the STREAMINFO alone and each frame only when its CRC-16 checks; a damaged, cut or empty frame becomes a silent frame of its length. Before, no damaged file hung it (24 tried) but a damaged frame shifted every later frame early (6 of 24 files kept 22-33 % of their samples in place); now 30 damaged files (frames cut, flipped, emptied; metadata flipped) end in at most 42 ms, every undamaged frame exact and in place, every damaged one silent.
- Opus of more than two channels (`cut-decode/src/opus.rs`): each multistream packet split into its streams (RFC 6716 appendix B framing), one Microsoft decoder a stream, channels put in the track's order by the mapping table, then (mapping family 1, 3 to 8 channels) in WebCodecs' order, L R C LFE then the surrounds (FFmpeg's `ff_vorbis_channel_layout_offsets`; that Chromium's AudioData has this order is from memory of its source, not read here), so the mix, which keeps the first two channels as the JavaScript's `stereo` does, plays left and right. Imported since 2026-11-17 (the refusal and its sentence are gone): `cut-app/tests/codecs.rs` imports 5.1 files and mixes them offline (a stream routed to L is heard left, to R right, to C not at all, as in the JavaScript). Proven with uncoupled streams (the fixture's mono packets as 1 and 3 streams, routed and silent channels, each of the six 5.1 positions); a coupled (stereo) stream is unproven: there is no stereo Opus source here and no Opus encoder.
- This PC (`tests/inventory.rs`): AV1 has a decoder (AV1VideoExtension, software: neither GPU has an AV1 DXVA profile) and no encoder, so AV1 stays unproven (no test media may be downloaded); VP9 Profile 2 (10-bit) has DXVA on both GPUs, but the VP9 encoder here makes 8-bit only, so it stays unproven; ALAC has Microsoft's decoder and encoder; Vorbis only an FFmpeg wrapper (refused).
- Vorbis (2026-11-17, `cut-decode/src/vorbis.rs`): the `lewton` crate (approved by the owner on 2026-11-16; it brought `byteorder`, `tinyvec` was in the tree) without its Ogg feature; Matroska/WebM `A_VORBIS` tracks (the headers Xiph-laced in CodecPrivate) decode on any PC. Each packet's samples are placed at its time plus what lewton gives early after a long block followed by a short one (libvorbis and WebCodecs give a packet the samples from the centre of the block before; lewton every finished sample), surround in WebCodecs' order like Opus. A refused packet leaves silence and starts the overlap again; headers whose codebooks ask for more than their bits hold are refused before lewton reserves memory for them (a damaged count would abort the process), sample rates above 768 kHz too, and lewton's calls run under `catch_unwind`. Proven on streams `tests/common/vorbis.rs` codes itself (a small Vorbis I encoder: flat floor 1, residue type 1, long and short blocks mixed; no Vorbis encoder is on this PC): the tones come back at gain 1.0000-1.0001 and 38-44 dB SNR, in place to the sample; a part decoded from cold equals the whole after one packet; 5.1 comes out reordered, mono as one channel; 400 damaged files (packets cut or bit-flipped, headers flipped or cut, files cut) never panic (no panic even inside lewton) and take at most 4 ms each, every undamaged packet's samples exact. `cut-app/tests/codecs.rs`: Vorbis alone and under VP9 import with their sound and mix at their levels. Unproven: files from a real encoder (libvorbis's floor 1 partitions, residue type 2, coupling), which are lewton's own ground. No Ogg reader: the JavaScript has none either (`main/cut/paths.js` refuses `.ogg`, `.oga`, `.opus`), and an Ogg packet that runs over a page boundary is not one byte range, which the sample tables need.

## Panels in their own windows (`cut-app/src/windows`, 2026-11-13)
Built: every panel but Tools opens in an OS window of its own (an egui immediate viewport: the panels borrow the shell mutably) from its tab's right-click menu, the Window menu (`window.detach.<panel>`, `window.dockAll`, also for `CUT_ACTIONS`) or by dragging its tab out of the main window; it comes back from its tab's menu, by closing its window, by dragging its tab onto the main window, or from the placeholder left in its slot. Per workspace, which panels are out and where (screen name, offset on it, size) is saved in the settings (`panelWindows`) and restored at start, clamped whole onto a screen there is; Reset to Saved Layout (`workspace.reset`) brings the workspace's panels back and resets its tabs and panel sizes. Keys typed in a panel's window run on the same shell (panel keys go to that window's panel), dialogs and toasts are drawn in the window last worked in. User-facing notes: `scratchpad/look-windows/design-notes.md`.
Proven: `tests/windows.rs` (model, settings, clamping, point mapping across scales; headless the menus, restart, workspaces, reset, tab drag-out, Korean, the Program monitor's picture in the window, and the main window's half of a relayed drag); the real app (`scratchpad/look-windows`): the Program monitor playing in its own window on the GPU frame route, Timeline and Program restored after a restart, an off-screen saved place clamped, dark/light and Korean/English, the tab menu, a tab dragged out, Space typed in the Program window.
Drags between windows (`windows/relay.rs`): while a button is held Windows gives the mouse to the window it was pressed in (winit calls `SetCapture`), which gets moves past its edges and the release; no other window sees anything. That window hands the drag (point, release, payload) to the window under the pointer, main or panel, and an egui plugin puts it into that window's next input (egui runs a plugin's input hook for immediate viewports too; eframe's own hook skips them). So a drag works both ways now: Project in the main window onto a Timeline in its own window, as well as from a panel's window onto the main window.
Frame time (measured, release, `scratchpad/look-windows-2`): the panel window's surface is presented inside the main window's frame, and with every surface in FIFO order one acquire a frame waits for the refresh; eframe subtracts that wait only when it is the main window's own. So eframe's frame time reads 15.8 ms or 3.5 ms by the phase of the frames (the panel's paint 13 ms or 0.9 ms, same build, quiet machine), 60 frames a second either way; three windows 14.8 ms, not three times one; with 10 ms of work added a frame the wait shrinks (paint 3.7 ms) and 60 frames a second hold. The report now has `windowsUiMsMean`, `windowsPaintMsMean` and `frameGapMsMax` to tell work from waiting. Deferred viewports (a frame per window, the shell reached through a thread-local) were built and measured: eframe 0.37 on Windows repainted the Program window at 60 Hz and the main window 14 times a second (404 of 540 frames dropped), so they were removed.
