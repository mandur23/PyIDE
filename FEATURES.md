# PyIDE feature modules

PyIDE is an Electron + Monaco Python IDE modeled on PyCharm. The core (`main.js`, `preload.js`, `renderer/core/`) owns the window, editor, tabs, project tree, and the registries below. Every IDE capability beyond that is a feature module that owns its own files.

## Layout of a feature named `foo`

- `main/features/foo.js` exports `register(ctx)`. It is loaded automatically at startup, after the main window has started loading, one module per event-loop turn. Use `ctx.ipcMain.handle('foo:…', …)` with channels prefixed by the feature name. Only plugin scripts may call feature channels: `core:features` answers after the last module registered, and core renderer code must not depend on a feature channel.
- `renderer/features/foo/index.js` is loaded automatically after Monaco and the core are ready, before the project opens. All plugin scripts are fetched in parallel and run one after another in load order (`async = false`). Wrap it in an IIFE and use the global `ide`.
- `renderer/features/foo/style.css` is loaded automatically if present. Reuse the CSS variables in `renderer/core/styles.css` (`--gray1`..`--gray12`, `--blue6`, `--green6`, `--red`, `--yellow`, `--mono`).
- `verify/foo.mjs` plus `verify/fixtures/foo/` hold the end-to-end check (see Verification).
- `renderer/features/foo/plugin.json` makes the feature a bundled plugin: `{id, name, version, vendor, description, main?: ['foo.js'], depends?: [ids], required?: true}`. `main` names its modules in `main/features/`. Disabled plugins load neither their renderer nor their main modules.
- `renderer/features/foo/locales/ko.json` holds its Korean strings (see Localization).

## Plugins

A plugin is a folder with `plugin.json`, plus optional `index.js`, `style.css`, `locales/<lang>.json`, and main-process modules listed in `main` (paths relative to the plugin folder). It uses exactly the same `ide` API as bundled features. Bundled plugins are the folders in `renderer/features/`. Installed plugins live in `<userData>/plugins/<id>/`. `plugins-catalog/` ships sample plugins that Settings › Plugins › Marketplace installs. `main/plugin-manager.js` owns discovery, enable/disable state (`<userData>/plugin-state.json`), install from a folder or `.zip`, and uninstall. Install copies with `copyTree`, not `fs.cpSync`, because in the installed app `plugins-catalog/` sits inside `app.asar` and `cpSync` cannot read an asar (`verify/plugin-install-asar.mjs`). It copies into `<userData>/plugin-new-*`, renames the installed folder aside to `<userData>/plugin-old-*`, renames the new one in and then deletes the old copy, so a folder another program holds (a helper running in it, an antivirus scan) is never left half deleted: the install fails with "The folder of <id> is in use by another program (EPERM). Close the program and try again." and the old version stays complete (if the second rename fails, the old folder is renamed back). Uninstall renames aside before deleting too. The staging and old folders sit in user data, outside `plugins/`, so discovery never sees them; the next install removes leftovers (staging folders only when older than 10 minutes, since another instance may be installing). Every change applies after a restart (`ide.restart()`), as in PyCharm. A plugin whose `depends` entry is disabled or missing does not load, so features must treat other plugins' APIs (`ide.lsp`, `ide.debugger`, `ide.run`…) as optional. Renderer scripts load in discovery order, except that a plugin's `depends` load before it, so it can use their APIs at load time. An installed plugin whose plugin.json is missing or not valid JSON is listed by its folder name as broken (`broken: 'missing' | 'invalid'`), never loads, and can be uninstalled from the Plugins page; the catalog and the Marketplace's "installed" ignore it, so the Marketplace offers Install to repair it. A main module that fails to load is reported as "Plugin <name> failed to load (<file>)" and kept per file by main/diagnostics (`diagnostics.loadFailure(file)`, not cleared with the error list); `plugins:list` gives its first line as `loadError`, and the Plugins page marks the row "Broken" or "Failed to load" with the reason (`#pluginError`) and offers no Enable/Disable for a broken one (`verify/env-failures.mjs`). Known limit: a renderer `index.js` that throws while it loads still looks healthy on the Plugins page (telling a load-time error from a later one needs a change in core's `loadFeatures`).

## Plugin Marketplace (online)

Settings › Plugins › Marketplace lists the sample plugins of `plugins-catalog/` together with an online index; for an id in both, the online entry wins when its version is newer. The index is the setting `plugins.marketplaceUrl` (gear › Manage Plugin Repositories…): an https URL, http on 127.0.0.1/localhost, or a local folder (its `index.json`) or `.json` file or `file:` URL. Unset, an installed copy uses `https://raw.githubusercontent.com/mandur23/PyIDE/master/marketplace/index.json`; source runs have none; `PYIDE_MARKETPLACE_URL` replaces the default (`off`: none; `verify/lib.mjs` sets `off`); an empty setting turns the online part off. Main reads it when the Plugins page opens (never at startup), at most every 10 minutes per URL unless Retry or the repository dialog asks again (`plugins:marketplace(value, {refresh})` -> `{plugins, online: {state: off|ok|error, error?, hidden?}, defaultUrl}`; each plugin has `origin: bundled|online`, `installedVersion`, `update`).

- Index format 1 (`main/marketplace.js` owns it and checks every field at the boundary; one bad field rejects the index with a message such as `Marketplace index is not valid: plugins[0].sha256 must be 64 hexadecimal digits`): `{format: 1, plugins: [{id, name, version, vendor, description, i18n?: {ko: {name, description}}, minIdeVersion?, url, sha256, size, homepage?}]}`. Ids are 2-64 lowercase letters/digits joined by `.`, `_`, `-` (no Windows device names); versions are semver; `url` is relative to the index or absolute (https, loopback http, or a local file when the index is local); `size` at most 20 MB; `homepage` https. A higher `format` says it needs a newer PyIDE. Index at most 1 MB, 500 plugins. Plugins whose `minIdeVersion` is above this version are hidden (the list says how many).
- Install (`plugins:installListed(id)`, from main's last listing, never a URL from the renderer): an online plugin first shows Install Third-Party Plugin (name, vendor, download URL, and a warning that plugins run with PyIDE's access). The download stops past the index's size, must match its size and sha256, and the zip's `plugin.json` must have the listed id and version; it then installs through `install(zip)`. Update appears in the Marketplace and on the Installed tab (row button, "Version x available" badge, Update in the details) when an installed plugin is older than the listed one. Changes apply after a restart, as before.
- Zips are unpacked by `main/zip.js`, not `tar`: no entry may leave the target folder (`..`, absolute paths, drives, `:`, device names, trailing dots, duplicate names, links), at most 50 MB packed, 100 MB unpacked and 2000 entries, each entry inflated only up to its declared size and CRC-checked. Names without the UTF-8 flag (Windows Explorer's compressed folders) are decoded as CP949 when they are valid CP949, else as CP437 (iconv-lite).
- Failed reads show "Could not load the online Marketplace", the reason and Retry above the bundled samples.
- Publishing: `node scripts/marketplace.mjs [plugins folder] [--out folder]` (defaults `plugins-catalog`, `marketplace`) zips each plugin folder reproducibly (sorted entries, fixed dates: an unchanged plugin keeps its sha256), writes `index.json` with relative URLs, validates it with the same parser, and removes zips the index no longer lists. `plugin.json` may add `minIdeVersion` and `homepage`. Commit `marketplace/` to `master`.
- Test: `verify/marketplace.mjs` (ports 9080-9081; `--pure` runs only the Node part): the script and the committed folder being current, the validator, zip-slip/bomb/CRC/link guards, install, tampered zip, version mismatch, update, offline, a CP949-named zip, a reinstall and an uninstall while a process runs inside the plugin folder (version 1 intact, readable error); then the page with a local HTTP server and a folder index (listing, search, trust dialog and Cancel, tampered download, install, update, bad index, offline and Retry, newer-PyIDE filter, empty = off), and after a restart the plugins running and the page, trust dialog and repository dialog in Korean.

## Editor groups, split panes and windows

`renderer/core/editors.js` owns the editor area. A document (one per file: `{path, model, savedVersion, encoding}`) can be shown in several editor groups. A group is a split pane with its own tab bar and Monaco editor, and groups form a split tree (Split Right `Ctrl+\`, Split Down `Ctrl+Shift+\`, drag a tab onto a pane edge, Unsplit). Clones share the model, so edits appear in every pane. Model decorations (`model.deltaDecorations`) and markers show in every pane automatically.

- `ide.editor` is the active group's editor and changes when the user focuses another pane. Never cache it. Anything attached to an editor (`onMouseDown`, `onDidChangeCursorPosition`, `addAction`, `createDecorationsCollection`, content widgets, view zones) must go through `ide.onEditor(editor => …)`. It runs for every existing editor and for each pane created later, including editors that viewers embed. It returns an unsubscribe function. `ide.editors()` lists them, and `activeEditorChanged(editor)` and `editorCreated(editor)` are events.
- Editor options that apply everywhere (font, wrap, rulers, bracket colors) go through `ide.updateEditorOptions(opts)`, never `ide.editor.updateOptions`.
- `ide.tabs` lists one tab per open document plus custom tabs. `ide.findTab(path)` prefers the active group. A file tab has `{kind: 'file', path, title, model, doc, group, pinned, preview}`. `ide.openFile(path, {line, col, focus, group: 'right'|'down'|'window'|group, preview, asText})`. Also `ide.closeTab(path, force)`, `ide.closeAllTabs(force)`, `ide.getDocument(path)`, `ide.saveAll()`, `ide.reloadFromDisk(paths)`.
- Do not rely on DOM ids inside the editor area except `#editor` and `#customHost`, which always belong to the first group. Put overlays in `#editorArea`.
- File viewers: `ide.registerFileViewer({id, icon, match(path), binaryOnly?, text?, mount(host, {path, doc, tab}) -> {dispose?}})`. A matching viewer opens in a custom tab instead of a text editor. `text: true` viewers also get the file's document (use `ide.createEditor(host, {model: doc.model})` to embed an editor that plugins attach to). `binaryOnly` viewers take only files the text loader rejects. "Open as Text" (tab menu, and a button in the binary viewer) bypasses viewers and reads even a file that looks binary as text.
- Detached windows ("Open in New Window", `Shift+F4`) run the same renderer with `ide.detached === true` and load only plugins whose plugin.json has `"detached": true`. They show only editors. A document open in one window is that window's alone; once another window opens it, main/windows.js holds the shared text and numbers the edits: each window sends Monaco's change deltas with the revision they were made on (`doc:op`), an edit made on an older revision is refused (`doc:nack`) and sent again shifted past the edits it missed (operational transformation in editors.js), so edits typed in two windows at once are all kept. When only one window is left the document is unshared again. Saves, reloads and encoding changes are told to the other windows (`doc:saved`), and renames and deletes too (`ide.documentsMoved(from, to | null)`, called by the tree, the refactor plugin and any plugin that renames files: documents follow with their unsaved text, tabs keep their group, position, pin and caret, deleted ones close in every window, compare tabs included). An explicit save of a document whose file no longer exists asks "{name} no longer exists on disk. Save it again?"; auto save skips it. Closing the main window asks once about every window's unsaved files (one Save Changes? dialog listing them; Save All saves each window's own, Cancel keeps every window), and closes nothing before the answer. Known limits: Convert line separators is sent as a full replacement, so an edit made in another window at that moment is lost, and text typed in a window in the one IPC round trip between opening a shared document and receiving its text is replaced by the shared text.
- Encoding: documents are read and written through `fs:readText` / `fs:writeText` (UTF-8, UTF-8 BOM, UTF-16 with or without a BOM, CP949), and the encoding is kept on save. A file that is not valid UTF-8 is CP949 only when CP949 decodes it cleanly; otherwise UTF-8 with replacement characters. UTF-16 without a BOM is recognized by its many NUL bytes beside ASCII ones (`main/text-codec.js`). Changes on disk (focus checks, auto save, File Cache Conflict) are checked by decoding the file in the document's own encoding (`fs:decode`); a reload, Load File System Changes and `ide.reloadFromDisk` detect the encoding again unless the user chose it (Reload in, Convert to, Open as Text pin it), so a file re-encoded elsewhere keeps its new encoding (the same text in another encoding is adopted only when the old encoding no longer reads the file). Convert to saves through the normal save (File Cache Conflict, save actions, other windows told), also for a modified document, and is undone with a message when PyIDE could not read the result back (BOM-less UTF-16 of Korean-only text looks binary). A CP949 save refusal (characters CP949 cannot store) is an `expected` error with a translated message, never an internal error. Plugins that write files that may be open should still use `fs:write` and then `ide.reloadFromDisk`.
- Safe save (`replaceFile` in main/text-codec.js): a save writes `.<name>.<pid>.pyide-tmp` next to the file and renames it over (a symlink's target is the one replaced), so a full disk or a crash never leaves a half-written file and a failed temp write leaves the original untouched. It writes in place, as before, for a new file, a hard-linked file (its other names see the save), a folder where the temp file cannot be created and a file held open without delete sharing; a read-only file is still refused. Known limits of the rename: the saved file gets the folder's inherited ACL instead of its own, and loses the Hidden and System attributes and alternate data streams (Zone.Identifier).
- Known limit: documents, tabs, Find in Files overrides, `ide.util.samePath` and main's shared-document key all use the lower-cased path, so in a folder with case sensitivity turned on (`fsutil file setCaseSensitiveInfo`) two files whose names differ only in case open as one document.
- Tests: `verify/encodings.mjs` (port 9270): stray-byte UTF-8, a reload encoding that sticks, re-encodings made outside, Convert to on a modified document and an unreadable conversion, the CP949 refusal (no internal error), a CRLF notebook, and the codec's safe write (a failed write, hard links, read-only). `verify/multi-window.mjs` (port 9271): edits typed in two windows at once (also random concurrent edits converging), a reload, rename (API and the tree's Rename) and delete across windows, a save of a deleted file, File › Exit with unsaved files in another window.
- Files dragged in from Explorer onto a pane open there (a pane edge splits, as for a tab), also over the editor text. The pane takes tab, tree-row and file drags in the capture phase, before Monaco's drop-into-editor (other drags, such as plain text, still reach Monaco), and offers files as a copy, since a copy-only source refuses 'move' and then sends no drop at all. A dropped path's kind comes from `ide.api.stat(path)` (`fs:stat` -> `{isDirectory, size, mtimeMs}` or null), never from a failed `fs:list`, which main records as an internal error. Tested in `verify/editors.mjs` (real CDP drags with file paths: the tab strip, over the text of an open file, a pane edge).

## Localization

UI text stays in English in the source and is translated by lookup, gettext style: the global `tr('Find in Files')`, or with placeholders `tr('Run {name}', { name })`. It is also available as `ide.t`. Each plugin's `locales/ko.json` maps the exact English string to Korean. A disabled plugin's file is not loaded, except for the entries for its `plugin.json` name and description, so the Plugins page still shows those in Korean. `renderer/locales/ko.json` covers the core. The language (`appearance.language`: `system`, `en`, `ko`) is fixed for a session, so call `tr()` wherever text is produced. Calling it at module load is fine. Static markup uses `data-i18n`, `data-i18n-title` and `data-i18n-placeholder`. Never translate user data: code, file names, paths, process output, package names, git messages. Keep product names (Python, Git, Pyright, ruff, pytest, pip, venv) and key chords in English, as PyCharm's Korean language pack does. Use PyCharm's Korean terminology, for example 프로젝트, 실행, 디버그, 터미널, 문제, 커밋, 구조, 설정, 인터프리터, 중단점, 단계 건너뛰기 (Step Over), 단계 진입 (Step Into), 단계 나가기 (Step Out), 프로그램 재개, 파일에서 찾기, 사용 위치 찾기, 이름 변경, 코드 서식 다시 지정 (Reformat Code), import 최적화. `verify/i18n-lib.mjs` has `englishLeaks(ctx, selector)`, which lists visible English UI text, and `missingTranslations(ctx)`, which lists `tr()` strings without a Korean entry. Launch with `launch({..., lang: 'ko-KR'})` to test Korean. Tests default to English. Pyright runs in the UI language: `lsp:start(root, python, locale)` passes it and main sets `VSCODE_NLS_CONFIG={"locale": …}` (Windows sets none of the variables Pyright otherwise reads), so its diagnostics are Korean in a Korean session (`verify/i18n-lsp.mjs`). Features that read Pyright diagnostics use `code` and the range, never the English message text; the import quick fix takes the undefined name from the diagnostic's range.

## Main-process context (`ctx`)

`ipcMain`, `app`, `send(channel, payload)` to the renderer, `startProcess(cmd, args, {cwd, env}) -> id` (output streams to the renderer as process events, see `ide.proc`; a pipe error is logged, never thrown, and a spawn that fails with ENOENT in a working directory longer than Windows allows (258 characters) prints "Cannot start <cmd>: the working directory path is too long for Windows (N characters): <cwd>"), `killProcess(id)`, `procs` (id -> ChildProcess, for stdin), `getWindow()`, `appDir`, `unpackedDir`, `vendorDir`, `diagnostics` (the IDE log and internal errors, see Diagnostics; also `require('../diagnostics')` from any main module).

`appDir` is `resources/app.asar` in an installed build: fine for `require` and `fs` reads, but other programs cannot open files inside it. Paths handed to another program (Python scripts, `ruff.exe`, pyright run as Node) use `unpackedDir`, the same tree on disk (`app.asar.unpacked`; equal to `appDir` from source), and must match `build.asarUnpack` in package.json. `vendorDir` is already under `unpackedDir`.

Bundled tools: `node_modules/pyright` (`langserver.index.js`, run with `process.execPath` and env `ELECTRON_RUN_AS_NODE=1`), and `vendor/` (a pip `--target` dir with `debugpy` and `ruff`; run ruff via `vendor/bin/ruff.exe`, and debugpy with the selected interpreter and `PYTHONPATH=vendor`).

## Renderer API (`window.ide`)

- State: `ide.root`, `ide.monaco`, `ide.editor`, `ide.tabs`, `ide.activeTab()`, `ide.findTab(path)`, `ide.currentInterp()` -> `{cmd, args, executable, version, label}`, `ide.interps`, `ide.reloadInterpreters()`. `ide.interps` comes from `py:interpreters` in `main.js`: the project's venvs (trusted projects only), `interpreters.extra`, then the py launcher and `python` from PATH, all probed at once. It keeps one entry per real file (`fs.promises.realpath` of each `sys.executable`), so a junction or an 8.3 spelling of a listed python.exe appears once in the status-bar picker (`verify/new-project.mjs` checks it). When `interpreter.<project>` names an interpreter that is not listed, main's `py:diagnose(root, exe)` (-> `{state: ok|missing|fails|untrusted, version|detail}`, stderr decoded as UTF-8, else CP949) says why: one that starts is added as a normal entry; one that is gone or does not start stays selected as `{invalid: true, reason, name, venv}`, with "Invalid interpreter: <name>" in red in the status bar and one warning notification per project, executable and state offering Choose Interpreter… and Recreate .venv. While it is selected `ide.currentInterp()` is null, so Run, the console and the rest say "No Python interpreter found." instead of running another Python, and code that falls back to another interpreter skips invalid entries (the New Project wizard, diagrams, Check RegExp, semantic highlighting). In Safe Mode project venvs are not started, as before. Entries older than Python 3.8 carry `unsupported: true` and the label "… [unsupported]"; selecting one warns once per executable ("need Python 3.8 or newer", with Choose Interpreter…) and it stays selectable. Test: `verify/interpreter-health.mjs` (port 9274).
- IPC: `ide.api.invoke(channel, ...args)`, `ide.api.on(channel, fn)`, plus `ide.api.read/write/list/stat/walk/exists/create/rename/trash/openFolder/openFileDialog`. `fs:realpath` resolves links, junctions and 8.3 names (the path itself when it cannot). `fs:walk` skips a folder below the root it cannot read (the root itself still fails). Errors from worker threads (`main/worker-host.js`: fs-scan, search, workspace) keep their `code` (EPERM, ENOENT), so diagnostics files a user's file problem on `fs:list` or `fs:walk` as expected, not as an internal error (`verify/tool-failures.mjs`).
- Events (`ide.on(name, fn)` returns an unsubscribe): `ready`, `projectOpened(root)`, `fileOpened(tab)`, `activeTabChanged(tab|null)`, `beforeSave(tab)`, `fileSaved(tab)`, `fileClosed(path)`, `filesChanged({created?, deleted?, renamed?})`, `interpreterChanged(interp)`, `problemsChanged`, `settingsChanged(key, value)`, `toolWindowShown(id)`, `treeRefreshed`.
- Files and tabs: `ide.openFile(path, {line, col, focus})`, `ide.openCustomTab({id, title, icon, mount(host, tab), onClose})` for non-text editors such as a diff view, `ide.closeTab(path, force)`, `ide.saveAll()`, `ide.reloadFromDisk(paths?)` after a tool rewrote files, `ide.isDirty(tab)`, `ide.renderTabs()`. A file tab is `{kind: 'file', path, title, model, savedVersion}`.
- Actions and keymap: `ide.registerAction({id, title, keys, run, when, terminal, context})`. While a terminal has focus, only actions with `terminal: true` fire (tool-window toggles do automatically), so programs such as Claude Code keep Esc, Ctrl+K, Ctrl+T and the rest. Keys look like `'Ctrl+Shift+F10'`, `'Alt+ArrowLeft'`, `'Shift Shift'`. The last registration wins on a clash, so use PyCharm's default keymap and do not take a key another feature owns (table below). `ide.runAction(id)`. The user can change any action's keys in Settings › Keymap (see Keymap editing), so read `action.keys` (or `ide.keymap.label(id)`) when showing a shortcut instead of writing it into the text. `context: 'editor' | 'projectView'` says where `when` lets the action fire (core's editor actions with `when: inEditor` get `'editor'`); two actions of different contexts never fire together, so Settings › Keymap does not report them as a conflict (Ctrl+D: Duplicate Line in the editor, compare's Compare With… in the project tree, as in PyCharm).
- Tool windows: `ide.registerToolWindow({id, title, icon, side: 'left'|'bottom'|'right', keys, order, mount(container, tw)})` returns `tw` with `show()`, `hide()`, `toggle()`, `isVisible()`, `setActions([{icon, title, run, id?, toggled?}])` (`id` becomes the button's `data-action`; a boolean `toggled` draws a pressed toggle button with `aria-pressed`), `setBadge(text)`.
- `ide.util.observeSize(el, fn)`: a ResizeObserver that calls `fn(contentRect)` in the next animation frame and only when the size changed, so a callback that changes layout cannot loop. Use it instead of `new ResizeObserver`. The browser's `ResizeObserver loop` notice is logged once per window as a warning, never listed as an internal error (`renderer/core/diagnostics.js`; test `verify/resize-observer.mjs`, port 9875).
- File type icons: `ide.fileIcon(nameOrPath, {dir})` returns a 16px icon element (PyCharm New UI file type icons, both theme drawings inside, CSS shows one) and `ide.fileIconType(...)` its type; names (Dockerfile, .gitignore, requirements*.txt...) win over extensions, unknown files get `anyType`. The table is in `renderer/core/file-icons.js`; the drawings are generated into `renderer/core/file-icons-data.js` by `tools/build-file-icons.mjs` (video, audio and PDF, which PyCharm lacks, are drawn in `tools/file-icons/`). Popup items accept an icon element. Test: `verify/file-icons.mjs` (port 9800).
- Toolbar and status bar: `ide.registerToolbarItem({side: 'left'|'right', order, el})`, `ide.registerStatusItem({order, el})`. The main toolbar follows PyCharm's New UI. Left: main menu (`Alt+\`), project widget, branch widget (vcs order 10), workspace home (20). Right, by order: right-side items ordered 60-99 go inside the run widget pill (run target 60, run 70, debug 80, stop 90), then Claude Code 150, Search Everywhere 180, settings gear 200. The interpreter picker is the status-bar widget; `ide.setInterpreter(executable)` selects one. `ide.icon(name, fallbackGlyph)` returns a PyCharm New UI SVG icon from `renderer/core/icons.js` (generated by `tools/build-icons.mjs`).
- Projects: `ide.beforeProjectChange` (an array of async hooks `(nextDir, {reload}) => false` to cancel, asked by `openProject`, `closeProject` and Trust Project before anything closes), `ide.openProject(dir)`, `ide.closeProject()` (back to the welcome screen, emits `projectClosed`), `ide.newProject()` (the New Project wizard, `renderer/core/project-wizard.js` + `main/new-project.js`), recent projects in the `recentProjects` setting. `ide.openProject(dir)` answers false when another open (or Close Project) started meanwhile: after each await (Trust, `beforeProjectChange` hooks, closing tabs, tree and interpreters) an overtaken open stops, so only the latest sets `ide.root` and emits `projectOpened`. Recent Projects is built from the list on disk (unless this window's own change is not written yet), so another instance's projects stay (`verify/core-lifecycle.mjs`). With no project the window is the welcome screen: `body.no-project` (set at startup without a project and by `closeProject`, removed by `openProject`) hides the tool window stripes, panels, splitters and the run widget, and `ide.actionEnabled(action)` is false for tool window activations (`needsProject: true`) and the run/debug actions (`PROJECT_ACTIONS` in ide.js), so `runAction` and the keymap refuse them and the main menu shows them, and View › Tool Windows, disabled. The layout change is CSS only, so a project opened afterwards gets its layout back as it was. In the New Project wizard the project types are a listbox (`ide.ui.listKeys`) and the interpreter lists keep one entry per python.exe (`fs:realpath`); Add Local Interpreter… with a file already listed selects that entry. Tested in `verify/new-project.mjs`. The main menu (`renderer/core/mainmenu.js`) lists actions by id and hides those whose plugin is disabled. Toolbar left: VCS branch 10. Bottom tool window orders: Run 10, Debug 15, Find 18, Hierarchy 19, Find in Files 20, Python Console 25, Terminal 30, Problems 40, Git 45, TODO 50, Python Packages 60, Coverage 65, Profiler 66, HTTP Client 68. Until a window is shown, an area's default window is the one with the lowest order.
- Project tree: `ide.registerTreeDecorator(entry => ({color, badge}))`, `ide.registerTreeAction({title, when(entry), run(entry)})`, `ide.refreshTree()`, `ide.revealInTree(path)`, `ide.selectedTreeEntry()`. The tree is a flat list of visible rows built from listings of the open folders: expanding or collapsing a folder lists only that folder (and its open subfolders, level by level in parallel) and splices its rows, and `refreshTree()` lists every open folder again. Only rows in view have DOM nodes (`#tree .node`, 24 px each), so code that looks for a row must scroll it into view first, and decorators run for drawn rows only (keep them cheap, a map lookup). Keys while the tree has focus: Up/Down/Home/End/PageUp/PageDown move the selection, Right opens or enters a folder, Left closes it or goes to the parent, Enter opens a file or toggles a folder, Delete moves to the Recycle Bin. Dragging a row onto a folder moves it there after a confirmation; dragging it onto an editor opens it (data type `ide.TREE_PATH_TYPE`). Files and folders dragged in from Explorer are copied (`fs:copyInto`, originals kept) into the folder under the pointer, the folder of the file under it, or the project root below the rows, as in PyCharm; names that exist there ask first (Copy: Overwrite, Skip, Cancel). Dropped anywhere else in the window they still open (a folder as the project). Tested in `verify/tree.mjs` with real CDP drags (`Input.dispatchDragEvent` with file paths), including a Korean folder with nested files, overwrites, and a mixed drop with failures. The context menu starts with PyCharm's New ›: File, Directory, Python File (Alt+Insert; core's own item only when no plugin offers Python File), Python Package and the plugins' items; an `ide.treeNewItems` item labelled New with a submenu is merged into it, other items stay at the top level (also tested in `verify/tree.mjs`). ## Untrusted content

Projects, notebooks, READMEs, HTTP responses, AI replies and program output are untrusted, and the IDE page holds the whole IPC API (files, processes), so content must never run in it. `main/security.js` keeps every window on the IDE page: navigations elsewhere (a clicked link, a dropped URL, `location.href`) are refused, `window.open`/`target=_blank`/middle-click open http(s) in the system browser and nothing else, `<webview>` is refused, and permissions (camera, microphone, location, notifications, devices, external protocols) are denied; only the IDE page may read the clipboard. A `file:` URL on a network share (`file://server/share/…`, which makes Windows sign in to that server) is fetched only from shares PyIDE runs from or the user opened a project, folder or file on (`allowShare`), so a docstring image in a Monaco hover cannot reach an arbitrary server; `main/security.js` owns the session's `webRequest.onBeforeRequest`. The preload exposes `window.api` only to the IDE's own `renderer/index.html` (passed as `--pyide-page`), and the renderer runs sandboxed. Show untrusted text with `textContent` (`el(tag, cls, text)`, a string `ide.ui.dialog` body), sanitize Markdown with an allowlist and handle link clicks (`a` and `area`) yourself, and put untrusted HTML in a sandboxed iframe without `allow-same-origin`. A Content-Security-Policy on the IDE page is not used because `srcdoc` frames inherit it, which would stop the scripts of notebook HTML outputs. Test: `verify/security.mjs` (port 9870).

## Verification

`verify/lib.mjs` launches an isolated instance: a temp copy of `verify/fixtures/<fixture>/` as the project, temp user data, and a CDP port. It returns `js(expr)`, `until(expr, label)`, `press('Ctrl+Shift+F')` (real key events), `type(text)`, `click(selector)`, `shot(file)`, `check(ok, label)`, `finish()`. A run fails on any failed check or uncaught renderer exception. See `verify/core.mjs`. Each feature uses its own port so instances can run side by side.
Temp folders: every `%TEMP%pyide-*` folder a suite makes (its launches' project copies and user data, and its own `mkdtempSync` folders, which `lib.mjs` registers by wrapping `fs.mkdtempSync`) is removed when the suite exits, after its instances are ended and their helper processes have let go (about 1.5 s). `PYIDE_KEEP_TEST_DIRS=1` keeps them for debugging. Clipboard: before a suite's first launch, `verify/clipboard-keeper.cjs` (a windowless Electron run) saves the OS clipboard (text, HTML, RTF, image) to `%TEMP%\pyide-clipboard-keeper`; a page hook notes whether a test window wrote to the clipboard, and at exit the last running suite restores it if it changed, so tests that press Ctrl+C never leave the user's clipboard replaced (`PYIDE_TEST_CLIPBOARD=off` turns this off). Pure-Node suites `verify/redact.mjs` (report redaction table), `verify/notifications-log.mjs` (batched log writes) and `verify/recovery-main.mjs` (crash recovery's main module) run in CI too. `verify/clean.mjs` (`npm run clean:tests`, `--age <minutes>`, default 360, `--dry-run`) removes what a crashed suite left; `lib.mjs` starts it detached at most once an hour. The `*-venv` folders in `verify/out` are reused caches and are not removed.
Process trees: suites that look for the processes PyIDE started use `lib.mjs`'s `processSnapshot()` (one `Win32_Process` query: pid, ppid, name, cmd, `created` in ms, working set, CPU ms) and `descendants(rows, rootPid, { includeRoot, since })`, never their own ParentProcessId walk. A child counts only if it started no earlier than its parent, because PIDs are reused: on the CI runner csrss/wininit/services, whose long-gone parent had PyIDE's PID, otherwise showed up as PyIDE's children. With the root gone, its children must have started after `since` (default: when the suite started). `verify/process-tree.mjs` (pure Node, in CI) checks this on a fake snapshot and on real child processes.
Core lifecycle: `verify/core-lifecycle.mjs` (ports 9276-9277; 9277 is the main process's Node inspector) checks overtaken project opens, `ide.util.errorText` (network, spawn, file and loopback texts), `project:exec` in a 287-character folder, a user plugin whose main module throws, and two leaks after a forced GC: Compare Files opened and closed 30 times (0 DOM nodes and listeners per round) and 12 project switches (project-watch's 'destroyed' listeners stay at 3).

## Semantic search (EmbeddingGemma 2)

`renderer/features/semantic` and `main/features/semantic.js` add meaning-based search with Google's EmbeddingGemma 2 (`google/embeddinggemma-2`, Apache 2.0) running locally. The model runs in a Python sidecar (`main/semantic/embed_server.py`) inside a private venv at `~\.pyide\semantic\venv` that reuses the system PyTorch. Setup adds only the torchvision build paired with that torch (the model's processor needs it even for text) and never replaces torch itself. The model itself sits in the standard Hugging Face cache. Files are split into code-aware chunks (functions, classes, and each method for Python; heading sections for Markdown; line windows elsewhere). They are embedded with the model card's CodeRetrieval prompts, truncated to 256 dimensions, and stored per project in `<userData>/semantic/indexes`. Only the shown project's index and the one shown before it stay in memory; another is released once its run has stopped and its changes are saved, and read again when needed. Only changed files are embedded again. The per-project index is an append log, `index.jsonl` (a header line, then one `[rel, record|null]` line per change; the last line for a path wins) plus the `vectors-<gen>.bin` its header names. Saves append the changed files 2 s after an update, the log is compacted into a new vector file once it is mostly stale, and pending changes are written at quit. Reading, chunking and (with the fake backend) embedding run on a worker; the main process reads and encodes the log in short slices, so indexing 20,000 files never holds it for more than ~50 ms at a time. Queries combine cosine similarity with a small keyword score. Other plugins can call `ide.semantic.query(text, {limit, similarTo})`. Tests use `PYIDE_SEMANTIC_BACKEND=fake`, a deterministic hashing embedder; `SEMANTIC_REAL=1 node verify/semantic.mjs` runs against the real model once `node verify/semantic-setup.mjs` has installed it.

What gets indexed: the walk (on the worker) leaves out `SKIP_DIRS`, virtual environments at any depth (`venv*`/`.venv*` names, `pyvenv.cfg`, `conda-meta`), whatever Git ignores (`git ls-files --others --ignored --exclude-standard --directory`; a folder that is not a repository keeps the old behaviour), folders excluded by the user (project tree context menu *Exclude from Semantic Index* / *Include in Semantic Index*, or the tool window's ⊘ action; stored in `<userData>/semantic/exclusions.json`), and data folders: more than `semantic.dataFolderFiles` files (default 1000) or `semantic.dataFolderMB` MB of indexable text (default 50), of which less than a fifth is source. A skipped data folder does not count toward its parent, so a package keeps its code next to a large fixtures folder. Settings › AI › Semantic Search holds both limits and `semantic.confirmChunks` (default 5000): a first index larger than that waits for a dialog listing its files, chunks and largest folders, where folders can be unticked; *Not Now* leaves the project unindexed until *Index Now* in the tool window. A run puts each file into the index as soon as its last chunk is embedded and saves every 40 batches or 20 s (and on pause and at quit), so a killed or restarted IDE resumes with the files not yet on disk. Indexing waits while the user types (the renderer sends `semantic:typing` while a run is going; 1.5 s of quiet resumes it), rests 30 ms between batches, and can be paused from the tool window or the project tree (`semantic:pause`, for every project until resume or the next launch). The status item shows the percentage and the time left from the recent rate. The sidecar uses half the threads torch would take (`PYIDE_SEMANTIC_THREADS` overrides) at below-normal priority. On a generated project with git-ignored `data/` (4,300 files), `outputs/` and `.venv-rvc/` plus a 1,500-file JSON `datasets/labels/`, the run went from 6,361 files / 6,901 chunks to 61 files / 601 chunks. `PYIDE_SEMANTIC_FAKE_PAGE_MS` slows the test backend per page of 200 files so verify/semantic.mjs can pause and kill a run part-way (ports 9530-9538).

## Database

`renderer/features/database`, `main/features/database.js` and `main/db/drivers.js` add PyCharm-style data sources. The driver table in `main/db/drivers.js` holds one entry per kind: SQLite (built in, Electron's `node:sqlite`), PostgreSQL (`pg`), and MySQL and MariaDB (both `mysql2`). Each entry carries its fields, default port, identifier quoting and an adapter with `query`, `schema` and `close`. External drivers install on demand with npm into `~\.pyide\db-drivers` (`PYIDE_DB_DRIVERS` overrides it). Data sources live in `<userData>/database/sources.json`. Passwords are encrypted with safeStorage and never reach the renderer, which only sees `hasPassword`. A saved password is kept on save or Test Connection only while the connection stays the same (`main/settings-sync/same-connection.js`: kind, host, port, user, database or file, and the URL without its password); changing any of them, or importing a source with the same id but another host, drops it so it is never sent to a different server. Errors cross IPC as `{ok: false, error, missingDriver}`.

The Database tool window (bottom, order 55) shows sources, schemas, tables, views and columns, loading a source's schema when it is expanded. A query console is a custom tab with a Monaco SQL editor over a result grid. Ctrl+Enter runs the selection or the statement at the caret; the splitter respects quotes, comments and `$tag$` bodies. Console text is saved under `<userData>/database/consoles/`. Opening a `.sqlite`, `.sqlite3` or `.db` file with a SQLite header adds it as a source. For server kinds, the data source dialog links to the Install Manager's Databases category. Tests: `verify/database.mjs` (ports 9600-9603); `DB_REAL=1` also installs the real `pg` driver.

## Install Manager

`renderer/features/installer`, `main/features/installer.js` and `main/installer/servers.js` add one tab (action `InstallManager`, Tools menu) for installing, updating and removing what a Python developer needs. An installable is a plain object pushed to `ide.installables`: `{id, category, name, description, size?, homepage?, status(), install(log, progress, signal), uninstall?, update?, start?, stop?, actions?: [{label, run, when?}], confirm?, confirmUninstall?}`, where `status()` resolves to `{installed, version?, running?, update?, detail?, available?, reason?}`. Built in are Python tools for the project interpreter (pip), portable PostgreSQL 18.6 and MariaDB 11.8.9 servers, and Git, Python 3.13, Node.js and the GitHub CLI through winget after a confirmation dialog. Other plugins add the PostgreSQL and MySQL drivers (database), EmbeddingGemma 2 (semantic) and Claude Code (terminal).

Main runs jobs in one queue per target (an interpreter's pip, winget, or one server), with cancel, streaming `installer:log` and `installer:progress`. Servers download with a pinned sha256 to `~\.pyide\servers\<name>-<version>` (`PYIDE_INSTALL_ROOT` overrides it), initialize with a generated password kept with safeStorage in `<userData>/installer/servers.json`, take the first free port from 5432 or 3306, run as children of the IDE and stop when it quits. A running server offers Add as Data Source, which calls `ide.database.addDataSource`. `PYIDE_INSTALLER_RUNNER` swaps the winget and detection runner for tests. Tests: `verify/installer.mjs` (ports 9620-9625); `INSTALLER_REAL=1` really downloads, starts, connects through the Database plugin, stops and removes both servers.

## AI runtime, completion and edits

`main/ai/runtime.js` owns the one private Python environment (`~\.pyide\semantic\venv`, reusing the system torch) and the JSON-lines sidecar client that semantic search and AI completion share.

Both sidecars unload when idle: once no request has been in flight for `ai.idleUnloadMinutes` (Settings › AI › AI Completion › Local Models; default 10, 0 keeps the models loaded), the client closes the server's stdin and the server exits on end-of-input with code 0, so the diagnostics never count it as a crash. A request in flight always completes first, because the timer is only armed while nothing is pending. The next request starts the server again and the status bar shows the plugin's usual loading hint ("Loading EmbeddingGemma 2…", "AI Completion: loading…") until the model is back. Main learns the setting from the renderer: each plugin sends `semantic:configure` / `ai-complete:configure` `{idleMinutes}` at load and on `settingsChanged`, the same way the plots plugin configures its main side, so main never parses `settings.json` itself. `node verify/ai-idle.mjs` (ports 9822-9823) checks the settings field with the fake backends and, when both real models are installed, unload, reload and the loading hint against them.

AI completion (`renderer/features/ai-complete`, `main/features/ai-complete.js`, `main/ai/complete_server.py`, `main/ai/complete-text.js`) shows Cursor-style ghost text from a local fill-in-the-middle model: Qwen2.5-Coder 0.5B by default or 1.5B (Apache 2.0, Q8_0 GGUF on llama.cpp through `llama-cpp-python`). ## Git merge, rebase and stash

`renderer/features/vcs-merge` (plugin `vcs-merge`, depends on `vcs`) builds on extension points the vcs plugin exposes as `ide.vcs`: `addBranchActions`, `addLogActions`, `addCommitHeader` and `setConflictHandler`, plus `invoke`, `notify`, `reload`, `openTextDiff` and `diffLines`. The branch popup offers Merge into Current…, Rebase Current onto…, Stash Changes… and Unstash Changes…. `git:status` reports `op` (merge, rebase, cherry-pick or revert) from the marker files in the git dir. While git is stopped, the popup leads with Resolve Conflicts…, Continue, Skip and Abort, the branch widget says Merging or Rebasing, and the Commit window shows the same controls above a separate Merge Conflicts group, whose files are never ticked for commit. Commands that can stop on conflicts go through `runStoppable` in `main/features/git.js`, which returns the conflicted files, and then open the Conflicts dialog: each file's change on Yours and Theirs, Accept Yours / Accept Theirs (`git checkout --ours/--theirs` and `git add`, or `git rm` where that side deleted the file) and Merge…. The merge tool is three Monaco editors, Yours | Result | Theirs. `mergeChunks` groups the base→yours and base→theirs hunks that touch into chunks (conflict, one side only, or the same change on both). The result starts as the base, and each side of a chunk is accepted (» «; the second side of a conflict is appended) or ignored (✕) from the strips between the panes. Apply writes the result and runs `git add`; the file's open editor shows the result before the tool closes (an editor with unsaved changes keeps them). During a merge, a commit takes the whole index (git refuses partial commits then) and the message is prefilled from MERGE_MSG. ## Packaging

`npm run dist` builds two Windows installers with electron-builder (config in package.json `build`): `dist/PyIDE-Setup-<version>.exe` (NSIS) and `dist/PyIDE-<version>.msi` (WiX, which electron-builder downloads into its cache). electron-builder rather than Electron Forge because its NSIS target does what the installer needs out of the box: a per-user install with no admin prompt (`perMachine: false`, `allowElevation: false`), a choice of install folder, a Start menu shortcut, an uninstaller, and `asarUnpack` globs. Forge's Windows makers are Squirrel, MSI and MSIX, so an NSIS installer would need a third-party maker. The build packs Electron from `node_modules/electron/dist` (no second download), keeps only the `en-US` and `ko` Chromium locales, and skips native rebuilds (`npmRebuild: false`), since `@lydell/node-pty` ships N-API prebuilds. `vendor/` is not in git: it must hold ruff and debugpy (pip `--target`) before you build. Do not edit files while a build packs `app.asar`: electron-builder reads them as it writes the archive, and a file that changes size mid-pack shifts the files after it.

- App code goes into `resources/app.asar`. Anything that another program opens is unpacked into `app.asar.unpacked` (`build.asarUnpack`): `vendor/` (ruff.exe, debugpy), `node_modules/pyright`, `node_modules/@lydell` (ConPTY binaries and the conout worker), and every `.py` under `main/` and `renderer/features/` (AI and semantic sidecars, the Python Console REPL, test runner helpers). Features build these paths from `ctx.unpackedDir` (see Main-process context). Monaco, xterm, marked and the locale JSON files load from inside the asar. Neither installer is signed.
- Icon: `build/icon.ico`, rendered from the welcome screen's "Py" tile by `node_modules\electron\dist\electron.exe tools/build-app-icon.js`.
- "Open with PyIDE" for `.py` files: a `PyIDE.py` ProgID plus a value in `Software\Classes\.py\OpenWithProgids` (NSIS: `build/installer.nsh`; MSI: `build/msi-project.js`, the `msiProjectCreated` hook that adds the same values to the WiX project). Neither changes the default program for `.py`, and each uninstaller removes only what it added. Launched with a file, PyIDE opens the file's folder as the project and then the file (the `file` query of `renderer/index.html`). It also opens a folder given on the command line.
- NSIS, per-user: `PyIDE-Setup-<version>.exe /S /D=<folder>`. Uninstall: `"<folder>\Uninstall PyIDE.exe" /S`.
- MSI, per-user by default (no UAC prompt) into `%LOCALAPPDATA%\Programs\PyIDE`: `msiexec /i PyIDE-<version>.msi /qn /l*v install.log`. Uninstall: `msiexec /x PyIDE-<version>.msi /qn` (or the product code). `msi.upgradeCode` is fixed (`C8A5FFE8-0263-4874-B6AC-E39E095BE819`), so a newer MSI upgrades an installed one in place. Deployment: run the per-user command in each user's context, for example an Intune Win32 app or Configuration Manager application with install behavior "user", or a logon script. For a machine-wide install, run `msiexec /i PyIDE-<version>.msi ALLUSERS=1 /qn` elevated (or as SYSTEM). That installs into Program Files with an all-users Start menu shortcut, and the "Open with" values go to HKLM (the hook writes them to HKMU). The machine-wide mode has not been tested here.
- The MSI has no dialogs (electron-builder `oneClick`), so double-clicking it installs per-user at once and starts PyIDE when it finishes. It has no install-folder choice (except `APPLICATIONFOLDER=<folder>` on the msiexec command line) and no running-app check, both of which the NSIS installer has.
- App data in `%APPDATA%\PyIDE` and `~/.pyide` survives either uninstall.
- WiX 4.0's `light.exe` is not long-path aware. When the checkout is deep enough that `dist\win-unpacked` paths pass 260 characters, `build/msi-project.js` points the WiX file sources at a temporary directory junction to `dist\win-unpacked` in `%TEMP%`, and removes the link when the build exits.
- `node verify/installed.mjs [nsis|msi|all] [installer file]` runs each installer in turn: it installs the build silently and per-user (NSIS into a temp folder, MSI into its default folder), then runs the installed `PyIDE.exe` over CDP. It opens a `.py` the way "Open with" does and checks Pyright diagnostics, the terminal, ruff reformat and the Git log. Finally it uninstalls and checks that the files, the shortcut, the install record and the `.py` registration are gone. Shells started by the Claude desktop app see that app package's private copy of `HKCU\Software\Classes`. There the NSIS installer's "Open with" values are checked in that copy, and the MSI's, which the msiexec service writes to the real registry, are checked from its verbose log.


## Updates

`renderer/features/updater` and `main/features/updater.js` update PyIDE with electron-updater and a generic feed.

- The feed is the setting `updates.feedUrl` (Settings › Updates). It is an http(s) URL, or a local folder (or `file:` URL) holding `latest.yml` and the installers, which the main process serves on 127.0.0.1 while PyIDE runs. Until the user sets it, an installed copy uses package.json `updateFeed`: the GitHub release tagged `pyide` in `mandur23/Portfolio-Nano-` (`https://github.com/mandur23/Portfolio-Nano-/releases/download/pyide/`). Source runs have no default, and `PYIDE_UPDATE_FEED` overrides it (`off` turns it off; `verify/lib.mjs` sets `off`, so tests never reach GitHub). An empty setting, typed by the user, turns updates off. `build.publish` names the same URL, so electron-builder writes `dist/latest.yml` and `resources/app-update.yml` (cache folder `%LOCALAPPDATA%\pyide-updater`); the feed in use replaces its URL at run time.
- Publishing a release: add a `## <version>` section to `CHANGELOG.md`, commit, then `npm run release -- <version>` on a clean `master` (`scripts/release.mjs`, plain Node, needs `gh` signed in). It checks the version is semver x.y.z and above package.json's, that tag `v<version>` exists neither locally nor on origin, and that local `master` contains origin's (read with `git ls-remote`, nothing fetched; behind or diverged stops it), sets it in package.json and package-lock.json (top level and `packages[""]`, formatting kept), runs `npm run dist` and checks `dist` for both installers, a `latest.yml` of that version whose sha512 matches the exe, and the exe's `.blockmap` (its blocks must add up to the exe's length), and runs `verify/installed.mjs all` through `verify/on-desktop.ps1`. It then commits `Release <version>` (author PyIDE), tags `v<version>` and pushes both with one `git push --atomic`, before anything is uploaded. Publishing to the `pyide` release (uploads use `--clobber`) uploads both installers, `PyIDE-Setup-<version>.exe.blockmap` and a copy of the exe named `PyIDE-Setup.exe` (the README's stable link), sets the title to `PyIDE <version>` and the notes (the changelog section in the usual frame, or `--notes <file>` as is), uploads `latest.yml` last (the moment installed copies see the new version), deletes older versions' files except the previous version's `PyIDE-Setup-<previous>.exe.blockmap` (the previous version is the newest one below this one on the release; copies of it need that blockmap for a differential update, and the run says whether it is there), and reads `latest.yml` back from the feed. A stop prints what to do for how far the run got: before the push, how to undo (`git tag -d`, `git reset --hard HEAD~1`; package.json is put back only when nothing was committed); after the push, not to reset but to finish with `npm run release -- <version> --publish-only`, which skips steps 1-6 and uploads from `dist` once `dist/latest.yml` names that version (hash checked) and the tag is on origin; after `latest.yml` is uploaded, that the release is live. That repository's other releases carry the Melody Breeze APK, which its site links as `releases/latest/download/…`, so the `pyide` release must never be Latest: every edit passes `--latest=false`, and if `gh release list` shows `pyide` as Latest afterwards the script sets the previous Latest back and fails. `--skip-tests` skips the installer tests. `--dry-run` runs the checks (problems become warnings), the build and the tests, prints the git and gh commands it would run, and puts the version and `dist/latest.yml` back; `--no-build` (a testing aid, `--dry-run` only) skips the build and checks whatever `dist` holds. The installer tests install the MSI into `%LOCALAPPDATA%\Programs\PyIDE`, the default folder of a per-user NSIS install, so with `Uninstall PyIDE.exe` there the script stops before building; `--replace-local-install` (refused while `PyIDE.exe` runs; it closes nothing) uninstalls that copy with `/S /currentuser` (settings in `%APPDATA%\PyIDE` stay), runs the tests and installs the new build there silently (the previous version's installer from `dist` if the tests failed). Once the uninstaller has started, every way out reinstalls, including Ctrl+C, Ctrl+Break and SIGTERM (their handlers also put the version back when nothing was committed). If the reinstall fails, the release stops before committing, exits non-zero and names the installer to run by hand. A dry run never touches that install. `PYIDE_DIST_DIR=<folder>` builds into that folder instead of `dist/` (also read by `verify/installed.mjs`), for when another program keeps files in `dist/win-unpacked` open and electron-builder fails with EBUSY. A beta (`npm run release -- 0.2.5-beta.1`) is built and tested like a release (electron-builder writes `dist/beta.yml` instead of `latest.yml`), committed and tagged `v0.2.5-beta.1`, and publishes only its installers and blockmap and then `beta.yml`: `latest.yml`, `PyIDE-Setup.exe`, the release title and notes and every stable version's files stay, so only Beta installs see it. Its notes are `## <beta>` or else `## <x.y.z>` in CHANGELOG.md (used by What's New; the release page is not edited). A stable release uploads `latest.yml` and a copy of it as `beta.yml` together, last, unless the release holds a newer beta, whose `beta.yml` and files then stay. Deletes: a stable release removes the files of older versions except the previous stable's and the previous beta's blockmaps; a beta removes only older betas' files except the previous beta's blockmap; newer versions are never removed. Step 8 reads back each channel file it uploaded.
- Checks: on startup (3 s after the main window is ready, unless `updates.checkOnStartup` is off; a version in `updates.skippedVersion` is passed over), then daily or weekly while PyIDE runs (see Periodic update checks at the end), and Help › Check for Updates… (`CheckForUpdates`), which also reports "latest version" and errors and ignores a skipped version. Settings › Updates has the feed with Browse…, the startup check, this installation's version and kind, the skipped version with Clear, and Check Now. Check Now shows its result on the page (`#updatesCheckResult`: checking, no feed, latest, a failure in red, a newer version) instead of a dialog over Settings (`ide.updater.check({report})`); only the MSI case, which has a choice to make, still opens its dialog.
- Deadline: a check has 30 s (`PYIDE_UPDATE_TIMEOUT_MS` in tests) and then fails with "The update server did not answer. Check your internet connection or proxy settings.": electron-updater's own timeout arms on a 'socket' event Electron's net requests never emit, so a server that accepts and never answers would keep it going. A timed-out check is abandoned and electron-updater's cached `checkForUpdatesPromise` is cleared, so the next check starts afresh. A check from the menu shows a "Checking for updates…" background task. Offline, timeout, HTTP (`HTTP_ERROR_*`) and feed (`ERR_UPDATER_*`) errors are marked expected: the dialog or the log tells them, not IDE Internal Errors. Test: `verify/env-failures.mjs` (a server that accepts and never answers, a 4 s deadline, a second check, an offline check).
- Channels (0.2.5): Settings › Updates › "Update channel:" Stable (default) or Beta (`updates.channel`, passed with `updater:check(feed, {channel})`). Stable reads `latest.yml`; Beta reads `beta.yml`, which every release keeps at the newest beta or stable version, so a beta install also gets stable releases, and reads `latest.yml` when the feed has no `beta.yml`. electron-updater turns `allowDowngrade` on when a channel is set; main turns it off again, so a copy switched from Beta back to Stable keeps its beta until a newer stable release comes out (the page says so). Versions order as semver (`0.2.5-beta.1 < 0.2.5-beta.2 < 0.2.5`, `compareVersions` in `main/features/updater.js`, which `scripts/release.mjs` also uses). What's New: `## 0.2.5-beta.1` headings are sections; a stable build leaves beta sections out, and a beta build also shows the section of the release it previews (`## 0.2.5` in 0.2.5-beta.1).
- An NSIS install (`Uninstall PyIDE.exe` next to `PyIDE.exe`) downloads the update in the background, differentially when it can (below), with "Downloading PyIDE 0.1.1… 42%" in the status bar (order 7), or "Downloading PyIDE 0.1.1 (delta 4.5 MB)… 42%" for a differential download. It then offers Restart to Update in the status bar and in a dialog with Skip This Version and Later. Restart saves modified files first, because the installer closes PyIDE even if a window would refuse. It then runs the installer silently (`--updated --force-run`), and the installer starts PyIDE again through its Start menu shortcut.
- Differential (delta) downloads (0.2.4): electron-updater rebuilds the new installer from the old one plus the blocks that changed, so a small release downloads a few MB instead of the ~98 MB installer (0.2.4 -> 0.2.5 test builds: 4.5 MB in 10 Range requests, 4.6%). What it uses, from `electron-updater` 6.8.9 (`NsisUpdater.doDownloadUpdate`, `AppUpdater.differentialDownloadInstaller`, `GenericDifferentialDownloader`): the old installer is `%LOCALAPPDATA%\pyide-updater\installer.exe`, which every NSIS install (and update) copies itself to; never the feed. The new installer's blockmap is `<installer URL>.blockmap`; the old one is `%LOCALAPPDATA%\pyide-updater\current.blockmap` if electron-updater kept one from the last download, else the new installer's URL with the new version replaced by the running one plus `.blockmap` (`<feed>/PyIDE-Setup-<running version>.exe.blockmap`), which is why a release keeps the previous version's blockmap. The changed runs of blocks come from the new installer with one single-range request each (`useMultipleRangeRequest: false`: GitHub's release downloads and the local folder server answer single ranges; the folder server answers `Range: bytes=a-b` with 206 and sends the whole file for anything else). The rebuilt file must match latest.yml's sha512. Any failure (no cached installer, a 404 for the old blockmap, no Range support, a hash mismatch, a corrupt cache) is logged by electron-updater (`Cannot download differentially, fallback to full download: …`) and the full installer is downloaded; `main/features/updater.js` wraps that step to log which happened (`downloaded 0.2.5 differentially: 4.5 MB of 98.2 MB`, or `differential download of 0.2.5 not possible …; downloading the full installer`) and to keep `download` ({mode: delta | full, size, bytes, reason: off | fallback}) in the updater state. A `current.blockmap` whose length is not the cached installer's (left by an update that was downloaded but never installed) is removed first, so the feed's blockmap is used instead of a hash mismatch. Off switches: Settings › Updates › "Download only the changed parts of an update when possible" (`updates.differential`, default on; passed with `updater:download`) and `PYIDE_UPDATE_DIFFERENTIAL=0`, which wins; both log the full download. 0.2.3 and older download 0.2.4 in full (they turned differential downloads off), and the `pyide` release had no blockmaps before 0.2.4, so the first differential updates are 0.2.4 -> the next release.
- An MSI install downloads nothing. Its dialog offers Download the new installer, which shows `PyIDE-<version>.msi` in a folder feed or opens `<feed>/PyIDE-<version>.msi`, because MSI installs are upgraded by Windows Installer. A source run only reports what the feed offers.
- What's New: `CHANGELOG.md` ships in the app. At startup main compares this version with `seenVersion` in `<userData>/updater.json` and records this one; the first window then shows "What's New in PyIDE <version>" with the `## <version>` sections newer than the one that ran before, up to this one (an older `updater.json` without `seenVersion`, from 0.2.4 or before: only this version's section; no `updater.json`, a fresh install: nothing). It shows once per update, and never in detached windows. Help › What's New (`WhatsNew`) lists every section up to this version. Sections are rendered as text: `- ` bullets become list items and backticks `code`. `PYIDE_CHANGELOG` replaces the shipped file in tests.
- IPC: `updater:state`, `updater:releaseNotes` ({version, afterUpdate (given once), all}), `updater:check(feed)`, `updater:download({differential})`, `updater:install`, `updater:openInstaller`, and the event `updater:state` ({kind, version, phase, available, percent, download}).
- Tests: `verify/updater.mjs` (ports 9800-9801, 9805, 9070) runs from source: no feed, a newer version, the same version and an unreadable feed in a local folder, the Settings page (with the differential switch and Check Now's results on the page), a skipped version, What's New (port 9805: after an update, the next start, Help, an older `updater.json`, a fresh install), the delta status text (states set with `PYIDE_UPDATE_TEST=1`'s `updater:testPhase`, which also takes an object of state fields), and Korean; the channels (port 9070: a Stable install sees 0.3.0 from latest.yml and not 9.9.9-beta.1 from beta.yml, a Beta install sees the beta, a stable release in beta.yml, latest.yml when there is no beta.yml, no downgrade on either channel, Check Now with the page's unsaved channel), and in pure Node the semver order and the What's New sections of betas. `verify/release-harness.mjs` also covers the beta channel (a beta uploads only beta.yml after its installers and leaves latest.yml, the title and stable files alone; a stable release uploads latest.yml and beta.yml last, keeps beta.yml at a newer beta, and keeps the previous stable's and beta's blockmaps). `verify/update-delta.mjs [--old <dir> --new <dir>] [--keep-builds]` (no CDP ports; not in CI: it builds) proves differential downloads without installing anything: without folders it builds this version and the next patch with `npx electron-builder --win nsis --x64 -c.extraMetadata.version=… -c.directories.output=%TEMP%\pyide-delta-*` (never `dist/`) and deletes them afterwards (~600 MB each). Each case runs `verify/update-delta-main.cjs`, a windowless Electron main process with the old version's package.json that registers `main/features/updater.js` as an NSIS install (`PYIDE_UPDATE_TEST_KIND=nsis`, honoured only with `PYIDE_UPDATE_TEST=1`), with `LOCALAPPDATA` in a temp folder whose `pyide-updater\installer.exe` is the old installer, and downloads through the real electron-updater and Electron net. It checks the downloaded file equals the new installer byte for byte and counts what the feed server sent: delta over http and from a folder feed (only the plan's ranges, both blockmaps read), a stale `current.blockmap`, fallbacks with no old blockmap on the feed, no cached installer and a corrupt one (sha512 mismatch), and both off switches; and that the real `%LOCALAPPDATA%\pyide-updater` is untouched. `verify/release-harness.mjs` (pure Node, in CI) runs `scripts/release.mjs` against a fake git/gh/dist: failure advice by phase, the order of a release, local-install handling, signals, and the blockmap rules (uploaded with the installers before `latest.yml`, previous version's kept, older ones deleted, a missing or mismatched blockmap stops the release, dry-run output). `verify/update-e2e.mjs [feed folder]` (ports 9802-9804) builds the next patch version into a temp feed (`-c.extraMetadata.version`). It installs `dist/PyIDE-Setup-<version>.exe`, updates it through the UI, and checks that PyIDE restarts by itself and comes back as the new version with its settings. With the MSI in `dist`, it also checks the MSI dialog. The installer restarts PyIDE as the signed-in user, outside the test's environment and profile, so the test closes that instance at once and starts it again with the test profile. It refuses to run while PyIDE is installed per-user in `%LOCALAPPDATA%ProgramsPyIDE`: the NSIS installer removes an existing per-user install before installing anywhere, so the test copy would uninstall the real one.
## Jupyter notebooks

`renderer/features/notebook` and `main/features/notebook.js` open `.ipynb` files as notebooks, like PyCharm's Jupyter support. The notebook is a `text: true` file viewer over the file's document: every change is written back into the document as nbformat 4 JSON (sorted keys, one-space indent and a final newline, as Jupyter writes it), so dirty state, Ctrl+S, close prompts and "Open as Text" come from the core. Fields the plugin does not edit (notebook and cell metadata, ids, attachments, `nbformat_minor`) are kept as they are; new cells get ids when the file is nbformat 4.5. The file's BOM and line separator are kept: the JSON is compared with the model's text as LF and, after `setValue`, the model gets its EOL back, so a CRLF notebook stays CRLF (`verify/encodings.mjs`). An empty `.ipynb` opens as a new notebook; invalid JSON or nbformat 3 shows an error with Open as Text. New Jupyter Notebook is an action and a project tree item.

## Diagnostics: IDE log and internal errors

The core part loads before everything else: `main/diagnostics` is installed at the top of `main.js`, and `renderer/core/diagnostics.js` is the first script in every window, main and detached. The required `diagnostics` plugin (`renderer/features/diagnostics`, `main/features/diagnostics.js`) is the UI.

- Log: `<userData>/logs/pyide.log` in idea.log's format (`2026-10-20 14:03:12,345 [ uptime ms]  LEVEL - #category - message`, stack traces on the following lines). It rotates by size to `pyide.1.log` … `pyide.5.log`. The level (DEBUG, INFO, WARN, ERROR) and the size cap (MB) are the settings `diagnostics.logLevel` and `diagnostics.logSizeMB`, read at startup and set in Help › Debug Log Settings…; `PYIDE_LOG_LEVEL` and `PYIDE_LOG_MAX_BYTES` override them. The log gets main-process `console` output, renderer `console.warn/error` and `ide.log`, failed IPC handlers with their stack, `ctx.startProcess` launches and exit codes (never the program's output), the debugpy adapter connection and failed DAP requests, and the stderr of watched sidecars. In main: `ctx.diagnostics.logger('#cat').info(msg)`.
- Internal errors: uncaught exceptions and unhandled rejections in the main process and every window, scripts that fail to load, `console.error(…, err)` with an Error, main modules whose `register` throws, renderer crashes, and sidecars that exit unexpectedly. `ctx.diagnostics.watchProcess(proc, {name})` watches a helper process: its stderr goes to the log, and a non-zero exit it did not ask for (`proc.kill()`, quitting) becomes an error with the last stderr lines as its trace. Pyright (lsp) and the AI sidecars (`main/ai/runtime.js`) are watched. Main has listeners for `uncaughtException` and `unhandledRejection`, so Electron's "A JavaScript error occurred in the main process" dialog never shows, and `dialog.showErrorBox` with that title becomes an internal error. Each error's plugin is the first stack frame inside a plugin's folder or one of its main modules (`plugins.ownerOf(file)`, so `renderer/features/<id>`, `main/features/<module>` and `<userData>/plugins/<id>`); without one it is PyIDE core. Identical errors are counted, not repeated. Report a caught error yourself with `ideDiagnostics.report(err)` (renderer) or `ctx.diagnostics.report({error, title})` (main). Not internal errors, on any IPC channel nor in the console.error hook: errors marked `expected: true` (a CP949 save refusal, "Debugging stopped" when the user stops a debug session that is still starting, `diagnostics.markExpected(err)`) and failures of the environment, whose code (or message prefix, for worker errors) is EPERM, EACCES, ENOENT, ENOSPC, EROFS, EBUSY, a network code (ECONNREFUSED, ECONNRESET, ECONNABORTED, ETIMEDOUT, ENOTFOUND, EAI_AGAIN, EHOSTUNREACH, ENETUNREACH, ENETDOWN) or Electron's `net::ERR_*` (`diagnostics.isEnvironmentError`). ## Local History and Bookmarks

`renderer/features/local-history` and `main/features/local-history.js` keep PyCharm's Local History, independent of Git. The main process owns one store per open project under `<userData>/local-history/<id>/`: `blobs/` holds each distinct content once (sha1, gzipped) and `index.json` lists each file's revisions `{t, h, k, l?}` (time, content hash or null once deleted, kind, label) plus the labels. As in PyCharm, a file is recorded from the first time it is opened in the editor or changes, so opening a project stores nothing (on a 20,000-file project the tree shows in about 0.4 s with or without the plugin). Revisions come from saves in the IDE (`fileSaved`), from a recursive watcher for changes made elsewhere (other programs, git, formatters, a detached window), and from rechecking the sizes and times of recorded files when the project opens, so their edits made while the IDE was closed are recorded too. Kinds: initial, save, external, create, delete, revert, checkpoint. A file seen first through a change counts as created only if it was born in the last 10 s. One burst of outside changes adds at most 200 files the history has not seen (a branch switch or a code generator records only the known ones). Only text files up to 1 MB outside `.git`, caches and virtual environments are kept. Reading, hashing, compressing and garbage-collecting blobs run on a worker thread (`main/worker-host.js` evaluates the same file with role `pyide-local-history`); the watcher callback only collects names, and all store operations run in one queue so a checkpoint right after a save sees the save. A burst can overflow the Windows change buffer; the watcher then reports a change without a name and goes quiet, so the store restarts it and rechecks the recorded files. Revisions older than `localHistory.days` (default 5) expire and the oldest go first above `localHistory.maxMB` (default 200), but the latest revision of every recorded file is always kept, so a file deleted long after its last change can still be recovered (Settings › Local History). Renames from the project tree carry a file's history along.

Several PyIDE instances can share the user data: every index write (the async flush and the one at close or quit) and every prune first re-reads index.json and merges it (revisions by time and hash, labels by time and text, the newer record wins); what a store removed itself (prune, size limit, rename) is tombstoned so it does not come back, a revision only this store lists whose blob the other instance collected is dropped, a revision with the same content as the one before it is left out (one change seen by both), and garbage collection keeps every blob the merged index uses. A blob stored again is touched so the other instance's 60 s grace covers it. Limit: two writes within a few milliseconds can drop the other's latest additions until that instance writes again; every instance writes with a merge when it closes the project or quits, so the final index has both. A file saved by another instance (a new file from the safe save's rename) gets a new birth time, so an instance that has not recorded it yet may label the change "Created". When a revision or the index cannot be written because of the environment (permissions, a full disk) the record is skipped and main sends `localHistory:writeFailed` ({root, dir, error}) once per store, which the plugin shows as one warning ("Local History is not being saved", the folder and the reason); history resumes by itself once the folder is writable, but a second outage in the same project session is not told again. Revert of a deleted file that is still open saves with `overwrite: true`, so it does not stop at the "no longer exists on disk" question. Test: `verify/history-instances.mjs` (ports 9282-9283; the write failure is in `verify/env-failures.mjs`).

`ide.localHistory.checkpoint(label, {paths})` adds a label and records the unsaved text of open documents (or only `paths`) first; saved ones are already on disk. The vcs plugin calls it in its `invoke` before every git command that rewrites the working tree (pull, checkout, rollback, merge, rebase, cherry-pick, revert, stash, unstash, accepting a side, resolving, continue/skip/abort), lsp before applying a workspace edit (rename, quick fixes), and ai-edit before the first accepted hunk of a Ctrl+I session. Show History (editor and project tree context menus, actions `LocalHistory.ShowHistory`, `LocalHistory.ShowProjectHistory`, `LocalHistory.PutLabel`) opens a tab: revisions and labels newest first, and a diff of the selected one against the current text. For a file the current side is its live document: Revert replaces the whole text as one undoable edit and saves it, and Revert Selected Changes (or Monaco's margin arrows) puts back only the changes touching the caret or selection. A folder's history lists every file under it; a deletion row shows the content just before it and Revert recreates the file, and a label row reverts every file that changed since the label. Each revert is preceded by a "Before Local History Revert" label.

`renderer/features/bookmarks` adds PyCharm's bookmarks: F11 toggles one on the caret line, Ctrl+F11 opens the mnemonic grid (typing 0-9 or A-Z assigns it at once, with an optional description), Ctrl+Shift+digit toggles a numbered bookmark, Ctrl+digit jumps to it, Shift+F11 lists all, and the Bookmarks tool window (left, Alt+2, order 25) groups them by file with their mnemonic, line and description (context menu: Jump to Source, Edit Description…, Delete). Gutter icons are glyph-margin decorations in the left lane (a ribbon, or a tile with the mnemonic). While a file is open its bookmarks are model decorations covering the line's text, so they move with inserted and deleted lines; a whole-text replacement (reload from disk) keeps their line numbers. They are saved per project in the `bookmarks.<root>` setting with paths relative to the root, and follow renames and deletions from the project tree.

Tests: `verify/history-bookmarks.mjs` (ports 9710-9712) saves, diffs, reverts selected changes and whole files, records outside changes, creations and deletions, recovers a deleted file, checks the label before a Git rollback, toggles, assigns and jumps to bookmarks, follows edits, edits a description in the tool window, restarts with the same user data, and repeats the surfaces in Korean.

## Refactorings

`renderer/features/refactor` (plugin `refactor`), `main/features/refactor.js` and `renderer/features/refactor/refactor_server.py` add PyCharm's Extract Variable (Ctrl+Alt+V), Extract Constant (Ctrl+Alt+C), Extract Parameter (Ctrl+Alt+P), Extract Method (Ctrl+Alt+M), Inline (Ctrl+Alt+N), Change Signature (Ctrl+F6) and Move (F6), the Refactor This popup (Ctrl+Alt+Shift+T) and the main menu's Refactor submenu (Rename stays lsp's Shift+F6). Action ids are PyCharm's (`IntroduceVariable`, `IntroduceConstant`, `IntroduceParameter`, `ExtractMethod`, `Inline`, `ChangeSignature`, `Move`, `Refactorings.QuickListPopupAction`). The project tree offers Move… for Python files and folders.

- Engine: rope (pure Python, LGPL) in the project interpreter. Measured on 2026-10-20 against the bundled Pyright 1.1.406: its `codeActionProvider` lists only `quickfix` and `source.organizeImports`, a code action request on a selected expression returns `[]`, and `textDocument/inlayHint` is an unhandled method (refactorings and inlay hints are Pylance features). Rope 1.15 did every refactoring on a three-module fixture in 4-140 ms per request, including rewriting imports across files. It runs in the project interpreter rather than the shared private venv because it parses with the running Python's `ast` (new syntax needs the project's Python) and resolves imports through that interpreter's `sys.path`, and the private venv only exists after AI setup. Rope is installed through the Install Manager's pip item (`pip:rope`, Python Tools). When it is missing, every refactoring offers Install rope, which runs that item and then retries.
- The sidecar speaks JSON lines, one process per interpreter. Each request carries the project root and the unsaved text of open Python documents. Rope reads files through an overlay file system and multi-step refactorings (Change Signature renames, then removes, adds and reorders) keep their intermediate results in memory. Nothing is written: the reply lists each file's old and new text and any moves. Each request opens a fresh rope project with `ropefolder=None`, so there are no stale caches and no `.ropeproject` folder.
- Rope's output is adjusted to read like PyCharm's. Extract Constant and Extract Parameter are implemented on `ast` instead (rope puts constants after the current function and introduces parameters only for plain names), and constants go after the imports. Move imports names as `from module import name` (rope's `add_import` is replaced), appends the moved definition to the destination (rope inserts it above a docstring) and creates a destination file that does not exist. Imports that rope drops although the module still uses them (or star imports) are put back, and PEP 8 blank lines are kept around new and removed definitions. Extract Parameter adds `name=<expression>` and leaves calls unchanged, as PyCharm does for Python, so it refuses expressions that read the function's locals. Change Signature renames the function and its parameters, removes, adds (with a default and/or a value for existing calls), reorders and changes defaults. Keyword-only parameters are kept as they are, because rope does not list them.
- With no selection, the Extract refactorings offer the expressions around the caret. Problems found before a dialog opens (no expression, a local in a constant, no function under the caret, syntax errors) show as an editor hint "Cannot perform refactoring. …". Problems with the dialog's input stay in the dialog. Rope's own errors map to these messages where they match and are shown verbatim otherwise.
- Every dialog has Preview, Refactor and Cancel. The preview lists the changed files and moves with a diff for each; Do Refactor applies and Cancel changes nothing. Removing a parameter the body still uses, or adding one with neither a default nor a value, always goes through the preview with a Problems detected note.
- Applying: each open document gets one undoable edit (a line diff, so carets and decorations elsewhere stay put), closed files are written with their encoding and line endings, and then files and folders move (their open tabs close and reopen at the new place). `ide.localHistory.checkpoint('Before Refactoring')` runs first when that plugin is present. Undoing the refactoring's edit in any of its documents (Ctrl+Z or Edit › Undo) undoes the whole refactoring: the other documents, the closed files (unless they changed since) and the moves. Redo (Ctrl+Shift+Z) works the same way. A file that moved has a fresh document with no undo history, so there the plugin takes Ctrl+Z and Ctrl+Shift+Z until the document is edited.
- Tests: `verify/refactor.mjs` (ports 9690-9691; it keeps a venv with rope in `verify/out/refactor-venv`) runs every refactoring through its key on `verify/fixtures/refactor`. It checks the code and imports in open and closed files, compares the fixture program's output before and after, and covers preview Cancel, cross-file undo and redo, the error messages, the install offer, inlay hints and the Korean UI.

## Inlay hints

`renderer/features/inlay-hints` (plugin `inlay-hints`, depends on `lsp`) shows inferred variable types (`count: int`), parameter names in calls (`net_price(price: 9.5, quantity: 4)`) and inferred return types (`def f() -> str`) as Monaco inlay hints. Pyright 1.1.406 has no `textDocument/inlayHint`, so the plugin finds the places in Monaco's tokens and asks Pyright for the text: hover for types, signatureHelp for parameter names (once per callee signature as its hover prints it; see Runtime performance). ## Coverage and profiling

An executor runs a configuration another way, as PyCharm's Run with Coverage and Profile do. `ide.run.registerExecutor({id, title, label(name), iconName, glyph, prepare(cfg, interp, session)})` adds it to the run widget's More Actions (⋮, next to Run and Debug), the gutter run menu and Rerun. `runConfig(cfg, {executor: id})` calls `prepare` before the type's `start`. `prepare` returns the interpreter to start with, or null to cancel. An executor can append arguments to `interp.args` that launch a wrapper script, which then runs the program's own command line (`-u script`, `-m pytest …`, or `-c` probes, which it runs unwrapped). This way scripts, pytest and the unittest runner all work without changes. `prepare` may push callbacks to `session.exitHooks`, which run once when that run's process exits. Remote interpreters (`interp.target`) are refused, since the wrapper exists only locally.

Coverage (`renderer/features/coverage`, `main/features/coverage.js`): `pyide_coverage_run.py` runs the program under coverage.py with branch coverage, measuring the project root as the source, so files that were never imported show 0%. It then writes a summary with executed, missing and partial lines (lines with a branch that never ran), and statement and branch counts. When coverage.py is missing, a prompt installs it into the project interpreter through the Install Manager's pip job (`pip:coverage`). The Coverage tool window (bottom, order 65) shows the folder tree with Line, % and Branch, % columns, using coverage.py's rounding, and double-click opens a file. Editors get 4px stripes in the line-decoration gutter: green for covered lines, red for missed ones and yellow for partial ones. Clicking a stripe shows "Covered 1/2 branches" and offers Hide Coverage. The project tree shows "N% lines covered". Hide Coverage / Show Coverage in Editors (setting `coverage.showInEditor`) toggles the stripes and badges. A new coverage run replaces the data.

Profiler (`renderer/features/profiler`, `main/features/profiler.js`): `pyide_profile_run.py` runs the program under cProfile and writes each function's calls, own and total time, and callers as JSON. Frames of the wrapper, runpy and the profiler are left out. The program's `<module>` becomes a root instead of a callee of runpy's `exec`, and calls from outside the program are kept as `root` entries. The Profiler tool window (bottom, order 66) has three tabs. Statistics is a table sortable by Name, Call Count, Time (ms) and Own Time (ms), with a filter. Call Tree expands the hot path. Flame Graph draws callers below callees; click zooms, Reset Zoom undoes it, and the tooltip shows time, share and calls. cProfile keeps caller and callee totals, not stacks, so the tree splits each function's callees across its callers in proportion to time, and recursion folds into the outermost call. Double-click, Enter or F4, or Navigate to Source in the context menu, opens the function's line. Tests: `verify/coverage-profile.mjs` (ports 9700-9701). It keeps a venv with pytest in `verify/out/coverage-profile-venv` and uninstalls coverage.py first, so every run installs it through the prompt. Set `COVERAGE_KEEP=1` to keep it.

## Python Console and Debug console input

- `renderer/features/pyconsole/pyide_repl.py` reads stdin in a thread and hands lines to the REPL loop and, while a statement runs, to `sys.stdin` (`ConsoleInput`: `input()`, `readline`, `read`, `.buffer`). On Windows the thread waits with `PeekNamedPipe` and reads only what is there: a read left pending on the pipe blocks other threads that query it (`GetFileType`), which a DLL's C runtime does when numpy's OpenBLAS loads. Stdlib modules cannot reproduce that hang, so `verify/dataview.mjs` (numpy and pandas in its venv) covers it, not `verify/pyconsole.mjs`. A line holding only `\x03` is Interrupt: SIGINT to the main thread while a statement runs (`signal.pthread_kill` on POSIX, `signal.raise_signal` on Windows, so `time.sleep` wakes too), and at a prompt it drops the block being typed; the session keeps its state. Stop still ends the process.
- The console sends what is typed before the first prompt, and what is submitted while earlier entries wait, one entry per prompt, so each echo sits right above its own output. While a statement runs the prompt is hidden (`.pyc-running`, after 150 ms, so quick statements do not flicker) and a typed line is the program's input: echoed as program input (`.stdin`), not as a `>>>` command and not into the history. Interrupt: Ctrl+C in the console input with no selection (with a selection it copies), the tool window's Interrupt button (`data-action="pyconsoleInterrupt"`) and `ide.pyconsole.interrupt()`.
- Debug (Shift+F9): the Debug console's stdin field (`#dbgIn`) takes the keyboard as the session starts, so an answer to `input()` never lands in the source file. Lines typed before debugpy has started the program are queued and sent once the process is attached; if the user moved the keyboard outside the Debug console meanwhile, it stays there. At a stop the editor gets the keyboard back from the hidden field. The Frames header names the stopped thread from the DAP `threads` response (`worker-1 · breakpoint`), not always MainThread.
- A console start that has not reached its first prompt ends when its process does, also when Stop or Rerun let go of it (`ended()`, which both run, settles it), so Rerun clicked twice quickly or Stop while the console starts never leaves the console unable to start.
- Debug start: main sends `debug:event {startKey, event: 'process', body: {id}}` as soon as it has spawned the debuggee, and the Debug console follows that process from then on, so its output shows live. A program that ends before debugpy listens (a Python debugpy cannot run on, an import error in sitecustomize) shows its own output and "Process finished with exit code N" instead of "Could not connect to debugpy … ECONNREFUSED"; main's own "The program exited before the debugger could connect" is `expected` and normally not shown. A startup the user stopped or replaced drains the output too, so nothing stays buffered. A Stop during a launch, an attach or Attach to Process rejects with an `expected` error ("Debugging stopped", `stoppedError()` in main/features/debug-attach.js), not an IDE internal error. The debugger matches debugpy's connection messages on the raw text, so a local ECONNREFUSED is never shown as "Cannot reach the server".

## Remote interpreters (WSL, SSH, Docker)

`renderer/features/remote-interp` (plugin `remote-interp`), `main/features/remote-interp.js` and the core library `main/remote/` add PyCharm's Add Interpreter › On WSL…, On SSH…, On Docker… and On Docker Compose… (Settings › Python Interpreter). A target is `{id, kind: 'wsl'|'ssh'|'docker'|'compose', python, distro | host, user?, port?, keyFile?, remoteDir? | image | composeFile, service, mountPath?}`, kept in the `interpreters.remote` setting after the form has connected and found Python. It joins `ide.interps` through `ide.interpreterProviders` with `executable` `<kind>://…#<id>` and a `target` field (plus the project root); its `cmd`/`args` are for display only.

- Routing: main features call `require('../remote')` for an interp with `target`: `startPython(ctx, interp, pyArgs, {cwd, env, forwards, onExit})` returns a process id like `ctx.startProcess`, `execPython` captures output, `debugEndpoint`, `terminal` and `pyrightPython`. Run, Debug, the test runner, the Python Console, Python Packages, the terminal and Pyright route through it. Not routed yet (local interpreters only): notebook kernels, the search-nav AST helper, viewers, workspace scripts, Install Manager pip items, venv creation and the AI/semantic setup.
- Every command is a POSIX `sh -c` script run by `wsl.exe -d <distro> --exec`, `ssh … <host>` or `docker exec` into the interpreter's dev container. `PathMap` (`main/remote/target.js`) maps Windows paths in arguments, `PYTHONPATH` (`;` → `:`) and the working directory to the target; a path the target cannot see is kept, so the program reports it instead of running something else. Paths the target prints map back for console traceback links through `ide.pathMappers` / `ide.toLocalPath(p)`.
- WSL sees every drive under its automount root (asked with `wslpath`), so the project is used in place; other Linux paths open as `\\wsl.localhost\<distro>\…`. The IDE's Python helpers and debugpy are copied into the distribution like for SSH, since importing them over WSL's `/mnt` file sharing takes many seconds per process. SSH: before each run the project is uploaded rsync-style to `~/pyide-projects/<name>-<hash>` (or the form's remote folder): a size+mtime manifest from the target, then only changed files as a gzip stream unpacked by the target's own Python (`main/remote/pyide_remote.py`); the IDE's Python helpers and debugpy (without Windows binaries) go to `~/.cache/pyide/helpers/<version>` once. Docker and Compose: one long-lived container per interpreter and project (`docker run -d` / `docker compose run -d`, named `pyide-<hash>`, label `dev.pyide.target`) bind-mounts the project at `/opt/project` and the helpers at `/opt/pyide` and publishes ports 5678-5680; pip installs last until the container is removed, and the containers stop when the IDE quits.
- Debugger: debugpy listens in the target; the IDE reaches it through WSL's localhost forwarding, an `ssh -L` tunnel or a published container port. `ready()` waits until the port listens in the target (`/proc/net/tcp`, never a probe connection, which would take debugpy's one client), and `attach` gets `pathMappings` so breakpoints and frames use local paths.
- Tests: with `PYIDE_TEST_REPORT=fd:3` and `PYIDE_TEST_REPORT_MARK`, both reporters write marked lines to descriptor 3, a copy of stderr that pytest's capture leaves alone (written directly: WSL refuses to reopen it as `/dev/fd/3`); `startProcess`'s new `opts.filter(text, stream)` takes them out of the output and writes them, with paths mapped back, to the local report the tests feature polls.
- Stop: the script prints its PID as a marker first; `ctx.killProcess` calls `proc.remoteKill` (set by the remote layer) so the program in the target ends, not only the local client.
- Terminal: with a remote project interpreter, a plain new session (not one opened with a chosen shell or command) is a login shell in the target, in the project folder.
- Pyright stays on this machine. A WSL-side Pyright would need Node in the distribution and would not cover SSH or Docker, so instead the target's library folders (site-packages and the like; only `.py`, `.pyi` and `py.typed`) are copied to `<userData>/remote-interp/libs/<id>` with the same manifest diff, and Pyright's `pythonPath` becomes a `python.cmd` there that answers Pyright's `sys.path` and version queries with the copies and the target's version. The standard library comes from Pyright's bundled typeshed for that version. The copy refreshes when the interpreter is selected, after pip install or uninstall in it, and from Settings › Remote Interpreters. Pyright still evaluates `sys.platform` checks for Windows.
- Secrets: SSH passwords and key passphrases are encrypted with safeStorage in `<userData>/remote-interp/secrets.json` and never reach the renderer or settings. ssh gets them through `SSH_ASKPASS`: the IDE's executable run as Node with a `--require`d script that reads the answer for a one-time token from a named pipe the IDE serves. Hosts without a secret run with `BatchMode=yes`.
- Detection: `wsl -l -v`, `docker version` / `images` / `compose version`, and the Host entries of `~/.ssh/config` (`PYIDE_SSH_CONFIG` overrides it). A kind that cannot work shows the reason in its form and in Settings › Remote Interpreters, which also syncs a target's libraries again or removes it with its password and caches. Main-side messages are translated by the plugin (`main/remote/messages.js`).
- Tests: `verify/remote-interp.mjs` (ports 9730-9731) puts stand-in `wsl.exe`, `ssh.exe` and `docker.exe` first on PATH (`verify/remote-fake`: pip's console-script launcher around `fakeremote.py`, a small sh interpreter over a path-mapped root that rejects Windows paths, running a venv in `verify/out/remote-interp-venv` as the targets' python3) and covers adding, Run, tracebacks, a breakpoint hit, pytest, pip list, the console, the terminal, Pyright, Stop, password hosts, unavailable kinds and Korean for each kind. `REMOTE_REAL=wsl`, `REMOTE_REAL=docker` or `REMOTE_REAL=ssh:<host>` runs the checks against what is installed (`REMOTE_WSL_DISTRO`, `REMOTE_DOCKER_IMAGE`) and skips with a message when it is not; `REMOTE_KINDS=wsl,ssh` limits a fake run.

## Conditional breakpoints

The debugger plugin's line breakpoints carry PyCharm's extra settings: `{line, condition, hitCondition, logMessage, enabled}`, saved with the other breakpoints in the `debugger.breakpoints:<project root>` setting and sent unchanged as DAP `SourceBreakpoint` fields in `setBreakpoints`, so debugpy does the work. `condition` is a Python expression evaluated in the frame. `hitCondition` follows debugpy: `3` suspends on the third hit only, `>= 3` from the third on, `% 3` on every third. A non-empty `logMessage` makes a logpoint: debugpy evaluates each `{expression}` in it, sends the text as an `output` event (shown in the Debug console) and never suspends there.

Ctrl+Shift+F8 anywhere else opens the dialog, whose list shows each breakpoint's condition, hit count and log message and whose detail pane edits the same fields (`bpFields` builds both).
- Glyphs: a red dot; a dot with "?" when there is a condition or a hit count (`.dbg-bp.cond`); a diamond for a logpoint (`.dbg-bp.log`), which does not tint its line. The hover lists the settings.

## .env files

Like PyCharm's EnvFile and VS Code's `python.envFile`, programs the IDE starts get the variables of `.env` files. `main/dotenv.js` owns the parsing and loading, in the main process only, so values never reach the renderer.

- Syntax (python-dotenv's): `KEY=value` (trimmed; ` #` after whitespace starts a comment, `a#b` keeps its `#`), an optional `export ` prefix, `# comment` lines, single quotes (literal), double quotes (escapes `\n \t \r \" \\ \$` and the rest of python-dotenv's set), quoted values spanning lines, and `${VAR}` / `${VAR:-default}` in unquoted and double-quoted values, resolved from keys earlier in the same or an earlier file, then the IDE's process environment (case-insensitively on Windows); unknown names expand to nothing. Lines that are not entries, and an unterminated quote's first line, are skipped and logged by file and line number only. `parse(text, lookup)`, `loadFiles(files, base)` (later files win; a missing file is skipped) and `withEnvFiles(env, envFiles, root)`.
- Run configurations: Python and pytest configurations have an Env files field (`envFiles`, `;`-separated, relative to the project root), defaulting to `.env`; configurations saved before the field existed get the default, and an empty field loads nothing. A listed file that does not exist (other than the default `.env`) prints "Env file not found" in the run console. The configuration's own environment variables override the files. Other types (Django, Flask, FastAPI) get the project's `.env`. `ide.run.envFiles(cfg)` gives the absolute paths, `ide.run.envFilesField` the field for other types.
- Launchers: `run:start` (7th argument), `tests:start` (`envFiles`), `debug:start` (`opts.envFiles`, forwarded by `ide.debugger.debugFile` from `cfg.envFiles`) take absolute paths; `undefined` means the project root's `.env` (the first root), which is also what the Python Console and a debug session started without a configuration get. New terminals load the project's `.env` while Settings › Terminal › "Load the project .env file into new terminals" (`terminal.loadEnvFile`, default on) is on; explicit `pty:create` `env` still wins, and remote sessions do not get it.
- Secrets: every loaded value of four or more characters (except booleans and short numbers) is added to the log scrubber (`addSecretValues` in `main/diagnostics/redact.js`), so it is masked in the IDE log, internal errors and Collect Logs even where a launch line carries it (remote interpreters put the environment on the command line).
- Highlighting: the `dotenv` plugin registers a Monarch language for `.env`, `.env.*` and `*.env` files (keys, `export`, values, escapes, `${VAR}`, comments).
- Test: `verify/dotenv.mjs` (port 9910) checks the parser and the scrubber as pure Node, then on `verify/fixtures/dotenv` Run, explicit overrides, several and missing files, Debug with the default and a configuration's own file, a test, the Python Console, new terminals with the setting on and off, the settings page, highlighting, and that no value reaches the IDE log.

## Dependency management

The packages plugin checks what the project declares against what the project interpreter has, like PyCharm's "Package requirements are not satisfied". `main/packages/deps.js` is pure (parsing, PEP 440, markers); `main/features/packages.js` does the I/O; the renderer half is in `renderer/features/packages/index.js`.

- Sources, in the project root only: `requirements*.txt` (options such as `-r`, `--find-links`, `-e`, paths and URLs are not packages; `\` continuations and `--hash` work), `pyproject.toml` (`[project].dependencies`, and `[tool.poetry.dependencies]` with `^`, `~`, `*` and `||` turned into PEP 440, `python` and `optional = true` left out; a pyproject.toml with neither is a tool config, not a dependency file) and `Pipfile` (`[packages]`). The manager is `uv` when `uv.lock` exists, `poetry` for `poetry.lock`, otherwise `[tool.poetry]` picks Poetry and `[tool.uv]` uv, otherwise pip. uv and poetry are looked for next to the interpreter (the Install Manager's uv item installs it there), on PATH, in `~\.local\bin`, `~\.cargo\bin` and `%APPDATA%\Python\Scripts`.
- Check (`packages:deps(root, interp, {texts, fresh})`): installed distributions and marker variables come from `importlib.metadata` run in the interpreter (not pip, so uv's pip-less venvs work; remote interpreters too), cached per interpreter until an install or `fresh`. Names compare as PEP 503 (case, `-`, `_`, `.`); specifiers follow PEP 440 including `~=`, `==1.2.*`, `===`, local versions and the exclusive `<`/`>` rules, and pre-releases that are installed count. A requirement whose marker is false (`; python_version < "3"`, `extra == "dev"`) is not required; a marker the parser cannot read counts as true. Unsaved editor text of open dependency files is checked, not the disk copy. It runs when the project opens, the interpreter changes, a dependency file is saved, edited (600 ms), created or deleted through the IDE, after every install from the Packages window, and when the window gets focus (re-reading the installed packages at most every 20 s).
- Results: a `warning` per unsatisfied line in problems source `dependencies` ("Package 'x' is not installed", "Package requirement 'x>=2' is not satisfied: 1.0 is installed"); a banner above the editor of the file, "N packages not installed / outdated" plus the names and Install (it sits in the editor group's body and moves the editor host down, so it never covers text; embedded editors get none); the same line with Install in the Python Packages window (`#depsSummary`) and the count as the window's badge. Alt+Enter (`ShowDependencyActions`, only while a dependency file has focus; Python keeps the lsp feature's) and the lightbulb offer "Install <pkg>" on a flagged line.
- Install (`packages:depsInstall`) runs in the Python Packages console with the command line shown: pip `install -r <file>` (cwd: the file's folder) for requirements.txt and `pip install <unsatisfied requirements>` for pyproject.toml / Pipfile; uv `sync --inexact` into the interpreter's venv (`UV_PROJECT_ENVIRONMENT`) for pyproject.toml, `uv pip install --python <interp> -r <file>` otherwise; `poetry install --no-root` with `VIRTUAL_ENV` set for a Poetry pyproject.toml. A quick fix installs only its requirement (`uv pip install` in a uv project, pip otherwise). When the project's tool is missing the banner says so and offers "Install uv…" (opens the Install Manager, which lists uv under Python tools) and "Install with pip"; PyIDE never installs a tool system-wide itself. Afterwards the package list and the check refresh.
- "Add to requirements" (Packages window, for an installed package no dependency file declares) adds `name~=version` to requirements.txt, else to `[project].dependencies` (created when missing), else to a new requirements.txt; an open file is edited in its editor when it has unsaved changes, otherwise written and reloaded (`packages:depsAdd(kind, text, requirement)` returns the new text).
- `ide.dependencies`: `check({fresh})` -> the state, `state()` -> `{manager, lock, tool: {name, path} | null, files: [{path, kind, editable, reqs: [{name, spec, raw, line, col, endCol, status: 'ok'|'missing'|'outdated', installed}]}]}`, `install(path, {specs, pip})`.
- Test: `verify/deps.mjs` (port 9920) builds three tiny wheels with zipfile, a temp project from `verify/fixtures/deps` with a `.venv` holding pyide-deps-other 1.0, and runs pip offline (`PIP_NO_INDEX`, `PIP_FIND_LINKS`): missing and outdated (with `_`/case-different names) are flagged with squiggles, banner and summary; the quick fix installs one; Install runs `pip install -r` and the banner, squiggles and summary go; Add to requirements; then a pyproject.toml with `uv.lock` (uv detected, marker-skipped item, banner per uv's presence, quick fix) and a Poetry pyproject.toml (`^`/`~` constraints).

## Live templates and postfix completion

`renderer/features/live-templates` adds PyCharm's live templates and postfix completion for Python, as Monaco snippets.

- Templates use PyCharm's syntax: `$NAME$` variables (the caret visits them in order of first appearance; a repeated name is mirrored), `$END$` for the final caret, `$SELECTION$` for the text Surround With wraps, `$$` for a literal dollar. Bodies indent with a tab, which Monaco turns into the file's indentation, and lines after the first get the current line's indentation. Built-ins: `main`, `iter`, `itere`, `compl`, `compli`, `prop`, `super`, `defm`, `defs`, `defc`, `with`, `try`, `pt`, `dataclass`, `fstr`, `log`, with default variable values in their `vars`. `dataclass` and `log` add `from dataclasses import dataclass` / `import logging` after the imports at the top of the file when it lacks them. The core's fallback provider (`renderer/core/python.js`) no longer offers `main` and `try`; `def`, `class` and `for` stay there.
- Expansion: Tab right after an exact abbreviation expands it, through the `liveTemplateAtCaret` context key the plugin keeps per editor and a Tab keybinding rule that also wins over the suggest widget, but not over visible ghost text or an active snippet. Templates are also completion items (kind Snippet, with a preview). Nothing expands or is offered inside a string or comment: `contextAt` scans the file from the top to the caret for `#`, quotes and triple quotes. A word that only ends in an abbreviation (`xmain`) or follows a dot is not a template.
- Postfix completion: `expr.if`, `.ifn`, `.nn`, `.not`, `.for`, `.enum`, `.print`, `.return`, `.len`, `.par`, `.with`, `.try`, `.main`, `.f`. `exprStart` scans back from the dot on the same line over names, attribute access, calls, subscripts, bracketed groups and string literals (bracket- and string-aware), so `foo(a, b).print` wraps the whole call. Statement templates (`if`, `ifn`, `nn`, `for`, `enum`, `return`, `with`, `try`, `main`) apply only when the expression starts the line. `.for` and `.enum` name the loop variable from the expression (`items` → `item`, `range(…)` → `i`). Tab expands an exact key; the completion list shows them after a dot with a preview, replacing only the key and deleting `expr.` with an additional edit, so they rank by the key like Pyright's members and sort after them.
- Surround With Live Template (Ctrl+Alt+J, action `SurroundWithLiveTemplate`) picks a template that contains `$SELECTION$` (`main`, `iter`, `itere`, `with`, `try`) and wraps the selected lines (the caret's line when nothing is selected), keeping their relative indentation.
- Settings › Editor › Live Templates lists the templates with a switch each, edits the abbreviation (user templates only), description and text, adds and removes user templates, restores a modified built-in, and switches each postfix template. Settings: `liveTemplates.custom` (`{abbr: {description?, body?, enabled?}}`: overrides of built-ins and user templates) and `liveTemplates.postfixDisabled` (keys).
- `ide.liveTemplates`: `templates()`, `postfix()`, `expand(editor)`, `surround(editor, abbr?)`, `toSnippet(template, selection)`, `exprStart(line, dot)`, `contextAt(model, pos)`, `candidateAt(editor)`.
- Test: `verify/live-templates.mjs` (port 9970): `main`, `iter`, `pt`, `itere`, `log` and `prop` with Tab and their first tab stops, the completion list, `items.for` picked from the list with its preview, `x.ifn`, `foo(a, b).print` and other postfix cases, strings, comments and docstrings, Surround With, and a user template, a disabled built-in and a disabled postfix template set in Settings that hold after a reload.

## Auto save and actions on save

The core save path (`renderer/core/editors.js`) runs save actions on every save and offers `ide.autoSave(paths?)`; the `autosave` plugin decides when to call it, as PyCharm's System Settings › Autosave does.

- Triggers (Settings › Appearance & Behavior › System Settings, all on by default): the window losing focus to another application or focus entering a built-in terminal (`autosave.onFrameDeactivation`; a blur only counts when `document.hasFocus()` is false, so an iframe taking focus does not, and test instances, which run with CDP focus emulation, never auto-save on a real OS blur); switching to another editor tab or pane saves the tab left behind (`autosave.onTabSwitch`); no key, mouse or text change for `autosave.idleSeconds` (default 15) saves everything (`autosave.onIdle`); Run, Debug and tests (which go through `ide.run.runConfig`) save all first (`autosave.beforeRun`).
- `ide.autoSave` skips untitled documents (`doc.untitled`, or a model that is not `file:`), read-only ones (`doc.readOnly`), documents open only in a viewer tab, a version whose auto save already failed, and files it cannot read or whose text on disk changed since PyIDE read or wrote it. Each document keeps `diskHash`, a fingerprint of that text, updated on load, save, `ide.reloadFromDisk`, a save from another window and Reload in an encoding. A skipped file emits `autoSaveSkipped({path, reason: 'changedOnDisk' | 'unreadable' | 'failed', error?})`, and the plugin shows it in the status bar (`#autosaveStatus`), whose menu offers Save (overwrite) or Reload from disk. Auto save never shows an error dialog; an explicit save still writes a changed file and still alerts on failure. Saves of one document are serialized.
- Save actions (Settings › Actions on Save): `ide.registerSaveAction({id, order, run(text, ctx) -> text | undefined})` with `ctx = {doc, path, auto, eol, modifiedLines, caretLines}`. They run on explicit and auto saves, in order, on the text; the result goes into the model as line-level edits (a Myers line diff) between two undo stops, so one Ctrl+Z reverts all of them and carets outside changed lines stay put. If the text changes while they run, an auto save is dropped and an explicit save writes the text as it is. Built in: strip trailing whitespace on modified lines (order 10, `save.stripTrailingSpaces`, on; lines edited since the last save are tracked as whole-line decorations; caret lines keep their spaces), ensure a final line break in the model's EOL (20, `save.ensureFinalNewline`, off), and from the tooling plugin optimize imports (30, `tools.optimizeImportsOnSave`, off) and ruff reformat (40, `tools.formatOnSave`, off). A Python file ruff cannot parse is saved unformatted.
- Settings pages from plugins may now use `group: 'appearance'` to sit under Appearance & Behavior.
- Test: `verify/autosave.mjs` (ports 9960-9961): defaults on the System Settings page, a window blur, a tab switch and a 1 s idle timer each write the file (and not with their setting off), untitled, read-only and in-memory buffers stay unwritten, a file changed on disk is not overwritten and shows in the status bar, each save action applies only when on (and also on auto save), Ctrl+S keeps the caret and one Ctrl+Z reverts all actions, and the Korean pages and warning.

## Crash recovery (hot exit)

`renderer/features/recovery` + `main/features/recovery.js`, like VS Code's hot exit. Every window (the plugin is
`detached: true`) backs up each modified document 2 s after the last edit (10 s for documents over 2 million
characters) and drops the backup when the document is saved, reverted, closed without saving or undone back to its
saved text; a 5 s sweep also catches a document marked saved without an edit (another window saved it, a plugin set
`tab.savedVersion`). Documents are found through Monaco's model events and `ide.getDocument`, so documents held by
viewer and compare tabs are covered too. Each PyIDE process writes to its own session folder,
`<userData>/backups/<pid>-<start ms>/`, made again on the next backup or within 10 s if something deletes it (the
windows are then sent `recovery:lost` and write every backup they hold again). Three failed backup writes in a row show
one error notification ("Unsaved changes are not being backed up", group Crash Recovery; counted per window), and a
successful write resets the count. `session.json` (`{pid, beat}`, written atomically every 10 s) is kept only for
PyIDE 0.2.6 and older running beside it on the same user data folder, which judge session folders by it. A backup file is
named by the SHA-1 of the document's identity (its lower-case path, or `untitled:<name>`) and holds one JSON line
(`path, name, untitled, project, language, encoding, lineSeparator, diskHash, asText, time`), a line break and the text;
it is written to `<file>.tmp` and renamed over. Windows editing the same document write the same file, and the main
process removes it only when no window holds it any more, so closing a detached window without saving keeps the
backup the main window still needs. A clean quit (`will-quit`, after every save prompt was answered) removes the
session folder; backups of a window whose renderer crashed are kept through it.

A session folder whose process is gone (pid not running, the same pid as this process, or a session that started more
than 10 min before this computer booted, which covers a reused pid) is a crash; a running process's folder is never
offered or removed, however old its heartbeat. With Windows Fast Startup a shutdown is a hibernation that keeps the boot
time, so a pid reused after one counts as running until that program exits (its backups are kept, not lost). Listing
reads only each backup's metadata line (the first 64 KB; `recovery:text` reads the text on Restore), and deletes dead
sessions' backups older than 30 days or of a project folder that no longer exists (a project on a drive that is not
connected, or on a UNC share, keeps them). A crashed session's backups are keyed by project (`project` is the main window's root when the
backup was written): the main window offers those of the project it opens (at startup once boot finished, then on
every `projectOpened`) plus those made with no project open; other projects' backups stay until their project opens.
A document backed up by several dead sessions is offered once, newest text. The dialog ("Restore Unsaved Changes",
`#recoveryDialog`) lists the files: Restore opens each with the backed-up text as an unsaved change on top of the disk
version (`ide.openFile(path, {text})`), keeps its line separator, and when the file changed on disk since the backup
puts the backup's `diskHash` back and sets `doc.conflict`, so an explicit save asks (File Cache Conflict) and auto save
skips it. Untitled documents and files that no longer exist come back in a new scratch file. The restored documents
are backed up by the new session before the old files are deleted. Discard deletes the backups; Esc keeps them for
the next start. After Restore or Discard the keyboard goes to the active tab, or to the Project view when that tab
cannot take it (the Workspace page). Settings › Appearance & Behavior › Crash Recovery (`recovery.backup`, on by default) turns backups off
(and drops the current ones). IPC: `recovery:hello`, `recovery:project`, `recovery:put`, `recovery:drop`,
`recovery:pending` (metadata and a `ref` per document, no text), `recovery:text(ref)`, `recovery:consume` (refs checked
against `<session>/<sha1>.backup`), and the event `recovery:lost`. Test: `verify/recovery.mjs` (ports 9060-9064, 9105):
debounce, metadata, save/undo/close remove the backup, one backup across a detached window, hard kill
(`taskkill /F /T`), Restore, a conflict after a disk change, Discard, focus after both, the setting, a clean quit,
Korean, then at 1008x681 the session folder deleted and made unwritable while running (backups written again, one
notification). `verify/recovery-main.mjs` (plain Node with a stand-in `ipcMain`, in CI): folder recreation, which
sessions are over, aging out, the metadata-only listing (four 40 MB backups of another project), `recovery:text` and
its ref check.

## Find in Files and Replace in Files

`renderer/features/search-nav` and `main/features/search.js` (matching runs on a worker). A regex is matched line by line unless it can match a line break (`\n`, `\r`, `\W` or a typed line break, Monaco's `isMultilineRegexSource`), on text whose `\r\n` are `\n`, so the preview and Replace in Files find what the editor's Ctrl+R finds (`\s+$` no longer eats a CRLF file's line breaks). Replacing copies the text between matches from the original unchanged (mixed separators survive), writes a line break the replacement adds with the file's own separator (CRLF when most of its line breaks are CRLF), and keeps a UTF-8 BOM out of reach of `^\s+`; unsaved buffers (`search:replaceText`) go through the same code. ## HTTP client

`renderer/features/http-client` (plugin `http-client`) and `main/features/http-client.js` add JetBrains' HTTP Client for `.http` and `.rest` files.

- Format: requests are separated by `###` lines (the rest of the line is the request's title). Before a request line come `#` / `//` comments, `# @name x` and `@var = value` lines; the request line is `METHOD URL [HTTP/1.1]` (a URL alone means GET), optionally continued by indented `?a=1` / `&b=2` lines, then headers, an empty line and the body. `< ./file.json` sends a file as the body (`<@ file` also substitutes variables in it, and `< file` lines inside a text body are spliced in). Response handler scripts (`> {% %}`), `>> file` and `<> file` lines are skipped. Multipart bodies have no special support. `ide.httpClient.parse(text)` returns `{vars, requests}`.
- Highlighting: a Monarch language `http` (states root, headers, body) colors separators, comments, `# @name`, `@var` lines, methods, header names, `{{var}}` everywhere and JSON bodies; Monarch never sees empty lines, so the first line after the request line that is not a header starts the body. Response JSON is colored by the same rules (language `http-json`) through `monaco.editor.colorize`.
- Running: a ▶ glyph (left lane) on every request line and Ctrl+Enter (the request containing the caret) send it to `http-client:send`. Main resolves the variables and sends with Node's `fetch`, so there are no CORS limits, following redirects, with `httpClient.timeoutSeconds` (default 60). Failures come back as `{ok: false, error: {kind: refused | dns | reset | timeout | url | file | other, target, detail}}`, which the renderer turns into a translated sentence ("Connection refused: nothing is listening at 127.0.0.1:9997.").
- Variables, resolved in main: `@var` lines above the request (their values may use other variables), then the selected environment, then `{{$uuid}}` (also `$random.uuid`), `{{$timestamp}}`, `{{$isoTimestamp}}`, `{{$randomInt}}` (0-999) and `{{$random.integer(a, b)}}`, then `{{name.response.body.field}}` / `{{name.response.body.$.items[0].id}}` / `{{name.response.headers.Location}}` from the last response of the request named `name` in this project (kept in main memory). Unknown names are sent as written and listed above the response as unresolved.
- Environments: `http-client.env.json` and `http-client.private.env.json` in the nearest folder from the request file up to the project root; private values override public ones, and `$shared` applies to every environment. Every private value is added to the log scrubber (`addSecretValues`) as soon as the file is read, and requests are never logged, so private values never reach the IDE log. Only environment names reach the renderer (`http-client:envs`); values appear there only inside a sent request shown in the panel. The environment is chosen per project (setting `httpClient.env.<root>`) in the tool window's selector, the status bar item "Env: …" shown for `.http` files, or the action HttpClient.SelectEnvironment.
- The HTTP Client tool window (bottom, order 68, Services icon) lists the last `httpClient.historySize` (default 50) responses of the session, newest first, and shows the selected one: method and URL, status, time, size and environment, then Body (JSON pretty-printed and colored, HTML as colored source with a sandboxed preview, images previewed, XML colored, other text as is, binary as its size), Headers and Request (the request as sent, with variables resolved). Double-clicking a history row or Go to Request jumps to the request.
- File › New HTTP Request (`NewHttpRequest`, also in the project tree's context menu) creates a `.http` file with an example request. The core already gives `.http` and `.rest` the HTTP file icon.
- Frameworks: `ide.frameworks.routeActions` (new) adds items to every route menu (view gutter icons, Endpoints); the HTTP client adds Generate Request in HTTP Client, which appends `### METHOD path` and `METHOD <route URL>` (with a JSON `Content-Type` and `{}` for POST, PUT and PATCH) to `generated-requests.http` in the project root and opens it there.
- Test: `verify/http-client.mjs` (IDE ports 9990-9991; local servers on 9995 and 9996 stand in for the dev and prod environments, nothing listens on 9997) checks highlighting, the gutter icons, GET through the gutter and POST with a JSON body through Ctrl+Enter, the status/time/size and pretty JSON in the panel, headers, `{{host}}` from the env file and switching dev to prod, a private env value, `{{$uuid}}` and `{{$timestamp}}`, named responses in a later request, `< ./payload.json`, HTML and image responses, a refused connection's message, the history, the log scrubber, New HTTP Request, the frameworks route action, and the Korean tool window.

## Spell checker

`renderer/features/spellcheck` and `main/features/spellcheck.js` (plugin `spellcheck`) add PyCharm's Typo inspection, offline.

- Dictionary: Hunspell en_US from `dictionary-en` 4.0.0 (SCOWL, "(MIT AND BSD)", 0.55 MB) read by `nspell` 2.1.5 (MIT, 42 KB). Both are plain dependencies, so electron-builder packs them inside `app.asar`. They run on a worker thread (`main/worker-host.js` `fileWorker`, role `pyide-spellcheck`) that reads them through Electron's asar support. The dictionary loads on the first check (about 120 ms, on the worker). IPC: `spellcheck:check(words)` returns the typos in a batch of lower-case words (a word the dictionary only knows capitalized, such as english, is accepted), `spellcheck:suggest(word, limit)` returns nspell's suggestions re-ranked so a swapped pair or a missing double letter comes first (nmae → name, coment → comment), and `spellcheck:read/writeProjectDictionary(root)`.
- What is checked: Python comments, docstrings and string literals (Monaco's comment and string tokens), and the names a Python line defines (def and class names, parameters, assignment targets including `self.x`, `for` and `as` names), not every name it uses. Also Markdown text outside fenced blocks, inline code, link targets and HTML tags (also in the Markdown viewer's embedded editor), and the Git commit message. Identifiers and prose tokens are split on snake_case, camelCase and digits, and each part is checked.
- Never flagged: parts under 3 letters, ALLCAPS, hex (`0x1f`, `deadbeef42`), URLs, e-mail addresses, paths, `%s` placeholders, any token holding a non-ASCII letter (Hangul and other scripts, accented words), Python keywords and builtins, a list of programming words (args, kwargs, json, http, utf, stdout…), and names that open Python files import or read as attributes of something other than `self`/`cls` (numpy's `linspace` and the like). These are harvested from the whole file when it is first checked and again on save.
- Checking: only lines in view (plus 10 lines above and below) of editors showing a Python or Markdown model, in `requestIdleCallback` slices of at most 8 ms, 300 ms after typing stops (150 ms after scrolling). Verdicts are cached per word, so only new words cross IPC. Each model keeps every checked line's typos. An edit shifts the lines below and rechecks only the changed ones, and a token change (an opened `"""`) marks lines dirty, keeping their typos until they are rechecked. Group editors and editors embedded by viewers are both tracked, since `ide.editors()` lists only the former.
- Display: Monaco markers with owner `spellcheck`, `MarkerSeverity.Hint` and code `typo`, message "Typo: In word 'x'". Problems sources use error, warning and info, and Pyright's hints carry the Unnecessary or Deprecated tags, so only typos are plain hints. style.css turns `.squiggly-hint` into a green wave (#6a9f62). Typos are not listed in Problems. An unchanged marker set is not published again, because a marker change restarts an open Alt+Enter request in Monaco.
- Quick fixes (Alt+Enter, the lightbulb): "Change to 'x'" for up to 5 suggestions (one undo step), "Save 'x' to project dictionary" and "Save 'x' to user dictionary". The action `Spelling.ShowActions` takes Alt+Enter only while the caret is on a typo in a `file:` editor or in the commit message box. In the editor it opens Monaco's quick-fix menu, so Python's Pyright actions appear too. In the commit box it opens a context menu. Notebook cells keep their own Alt+Enter.

## Renaming and moving modules from the project tree

Renaming or moving a Python module or package in the project tree rewrites its imports, as PyCharm's Rename and Move with Search for references do. The core tree offers `ide.treeMoveHandlers` (`handler({kind: 'rename'|'move', entry, dir})` resolves true when it handled the request, else the plain rename or move runs) and `ide.moveTreeEntry(entry, to)`, the plain rename or move. A plain rename or move renames on disk and then carries the open documents at or under the old path, unsaved text included, to the new path in every window (`ide.documentsMoved`); nothing is saved first, so a read-only file, a file in File Cache Conflict or a folder holding one keeps its edits. Delete closes the deleted documents' tabs in every window. Rename runs from the context menu, Shift+F6 while the tree has focus, and moves from dragging a row onto a folder or Ctrl+X then Ctrl+V on a folder (or a file in it), also Cut and Paste in the context menu. The refactor plugin takes over for a `.py` file other than `__init__.py`, a package and a namespace package (a folder without `__init__.py` that holds `.py` files) inside a trusted project; other files and untrusted projects keep the plain prompt and confirmation.

- Rename shows "Rename module 'geo.shapes' to:" (or package) with the file name, the part before `.py` selected, and Search for references on, with Preview, Refactor and Cancel. Moves open the Move dialog with the drop target as the destination and the same checkbox (also the tree's Move… item). With it on, `refactor_server.py` runs rope's `Rename` on the module or package resource (`renameModule`) or `MoveModule` (`move`), so `import a.b`, `from a import b`, `from a.b import f`, aliases and relative imports are rewritten in every project file. The result is applied like every refactoring: open editors get one undoable edit each (their unsaved text is what rope read), closed files are written, the open files under every moving path are saved first (`saveMoving`; if one stays modified nothing changes and the user sees "{name} has unsaved changes that could not be saved, so it was not moved.", also before an undo or redo replays a move) and their documents then follow to the new place in every window (`ide.documentsMoved`), Local History gets "Before Refactoring", and one Ctrl+Z undoes it all. With it off, or for a module renamed to a name without `.py`, only the file or folder is renamed.
- rope's output is adjusted: a namespace package gets a temporary empty `__init__.py` while rope analyses it (rope refuses or fails on namespace folders), changes that only touch blank lines are dropped (MoveModule strips them in the moved module), and the imports MoveModule rewrites keep their place in the import block instead of moving to its end. A move keeps each importer's style, as PyCharm does: rope turns relative imports into `import tools.figures` with qualified uses (and fails on `from ..pkg import mod`), so before rope runs, the relative from-imports that name the moved module (or its name) are made absolute in memory (`absolutize_importers`), and afterwards those imports, now naming the new place, become relative again when the new place is in the importer's top-level package (`from ..views.price import total`, `from . import price`), else stay absolute (`from tools import figures`) (`relativize_importers`). Dotted names are taken relative to rope's source folders (`project.get_source_folders()`, deepest first), so in a src layout `src/shop/models/price.py` is `shop.models.price`; an absolute name is used only when rope's `find_module` resolves it to the module the relative import names (other source folders holding the importer are tried next), and an importer without one is left to rope unchanged. Call sites stay unqualified; `import a.b` (also `as c`) importers keep the qualified style with the new path. Rope may still merge two from-imports of the same new package into one statement.
- Without rope the Install rope offer has a second button, Rename Without References or Move Without References. Move on a folder from the tree no longer reads the folder as a file (it failed before).
- Test: `verify/rename-module.mjs` (ports 9110-9112, the third instance a src-layout project with `src/shop` and `tests/`, rope from `verify/out/refactor-venv` as in verify/refactor.mjs) renames a module with Shift+F6 (unsaved text in the module and an importer, absolute, from, dotted, aliased and relative imports, open and closed files, undo and redo), renames a package through the preview, moves a module with Ctrl+X / Ctrl+V, a namespace package by drag-and-drop and a module with relative (`from .x import y`, `from ..pkg.x import y as z`, `from . import x as a`), `from pkg import x` and `import a.b [as c]` importers with Cut / Paste in the context menu (exact resulting text), renames with the checkbox off, checks that a `.txt` file and an untrusted project keep the plain prompt, uses the rope offer's fallback, and checks the Korean dialogs; the fixture program's output must not change. ## Keymap editing

Settings › Keymap (`renderer/features/settings`) edits the keymap like PyCharm's: select an action, then Add Keyboard Shortcut… (a capture box records the next key press with its modifiers, Shift twice is Double Shift, and *Second stroke* adds a two-stroke shortcut such as `Ctrl+K C`, shown as "Ctrl+K, C"), Remove Shortcut (a menu when the action has several), Reset Shortcuts and Reset All; double-click or the row's context menu does the same. The capture box warns when the chord is taken (the same key, or one is the other's first stroke, by an action that can fire in the same place: actions with different `context`s are not conflicts) and OK then asks PyCharm's question: Remove (the other assignments), Leave (both keep it) or Cancel. Modified actions are blue, and *Show modified only* filters to them. Changes wait for OK / Apply.

- Storage: only the user's changes, `keymap.overrides` = `{actionId: [keys]}` (an empty list means no shortcut). The core (`renderer/core/ide.js`, user keymap block) keeps each action's `defaultKeys` and sets `keys` from the override, at registration (so plugin actions registered later, also on `ready`, get theirs) and live on `settingsChanged`, then emits `keymapChanged`. Defaults of untouched actions can change in later versions. Overrides for ids that are not registered stay in the setting; values that are not lists of keys, and keys that are not `comboOf` strokes (`Ctrl+Alt+Shift+K`, two strokes, `Shift Shift`), are ignored. API: `ide.keymap.comboOf(e)`, `isValid(key)`, `parse(raw)` -> Map, `isModified(id)`, `format(key)`, `label(id)`.
- Dispatch: the global keydown handler also takes two-stroke shortcuts: a first stroke that starts an enabled action's two-stroke key is swallowed and waits up to 1.5 s. When the wait runs out or the second stroke completes nothing, the first stroke's own single-stroke action runs (Ctrl+K Commit… beside a `Ctrl+K C` chord, as in PyCharm and VS Code) and the second stroke is then handled as an ordinary key; Escape just cancels.
- Where shortcuts show: Find Action, Search Everywhere and the main menu read `action.keys` when they open (`menuHint` only for actions without keys, such as Undo). A tooltip follows the keymap when its element has `data-keymap-action="<id>"`; the title's trailing "(keys)" is replaced on hover (toolbar main menu, Search Everywhere, Hide, Run, Stop, every tool window stripe button). Tool window `tw.keys` comes from `tw.keyAction` (`Activate<id>ToolWindow`, or AI Chat's `AiChat.Toggle`).
- Monaco: an action whose `run` (or the action) carries `editorCommand` (core's editor actions: Duplicate Line, Delete Line, Comment with Line Comment, Go to Line, Find, Replace, Extend/Shrink Selection, Move Line, Collapse/Expand) keeps Monaco's own keybindings while unmodified. Once modified, the settings plugin removes every default Monaco keybinding of that command (`{keybinding: 0, command: '-cmd'}`) and binds the action's keys to it with `monaco.editor.addKeybindingRules`, so embedded editors (viewers, notebook cells, consoles) and Monaco's context menu follow the keymap and the old key no longer runs it anywhere.
- Test: `verify/keymap-edit.mjs` (ports 9120-9122): rebinds Tool Window: Project (old key dead, new key works, tooltip, More list), the Leave and Remove conflict choices, Remove and Reset, a two-stroke Duplicate Line, Comment with Line Comment in the editor and in an embedded Monaco editor, Find Action and main menu hints, persistence across a restart, malformed and `__proto__` overrides, a late-registered action, Reset All, and the Korean page and dialogs.

## Attach to Process

Run › Attach to Process… (`AttachToProcess`, Ctrl+Alt+F5, as in PyCharm) debugs a Python program that is already running outside the IDE. `main/features/debug-attach.js` (a main module of the debugger plugin) lists the processes and injects debugpy; `main/features/debug.js` (`debug:processes`, `debug:attach`) runs the DAP session; `renderer/features/debugger/index.js` has the dialog and the session.

- The dialog lists local `python*` processes with their pid, command line (without the interpreter) and interpreter (version and path; a venv's launcher stub is folded into the real interpreter it starts), filtered as you type (pid, script, command line, interpreter); Up/Down/PageUp/PageDown move, Enter or a double click attaches, Refresh lists again. Processes whose command line (or, on Linux, working directory) is inside the project come first under "In this project", then the rest, newest first. Windows has no cheap way to read another process's working directory, so there only the command line counts. Listing is one `Get-CimInstance Win32_Process -Filter "Name like 'python%'"` (about 0.7 s, 10 s timeout) plus one cached `python -c` version probe per interpreter; elsewhere `ps`. Left out: PyIDE's own Python (anything whose command line points into the app folder, `app.asar.unpacked`, `vendor/`, user data or `~/.pyide`: the REPL, semantic and AI servers, refactor, notebook kernels, coverage/profiler bootstraps), debugpy adapters and processes already run under `-m debugpy`.
- Attaching runs `<target's python.exe> -X frozen_modules=off -m debugpy --listen 127.0.0.1:<port> --pid <pid>` with `PYTHONPATH=vendor` (the target's own interpreter, so Python 3.14's `sys.remote_exec` matches its version; debugpy falls back to its DLL injector otherwise), then connects to the port and sends the same `initialize`/`attach` (`redirectOutput: true`, so the program's output reaches the Debug console)/`setBreakpoints`/`configurationDone` as a launched session. Breakpoints, stepping, frames, variables, watches, evaluate and inline values all work unchanged; stdin is not connected. A process can call `debugpy.listen()` only once, so a process attached before (remembered per pid, or found from its debugpy adapter child's `--port`, which also covers programs that call `debugpy.listen()` themselves; marked "debugpy listening") is connected to directly, in about 0.3 s instead of 3-5 s.
- Stop/Ctrl+F2 (titled Detach while attached) and Rerun: Stop sends `disconnect` with `terminateDebuggee: false` and never kills the process; Rerun attaches to the same process again. The session ends on its own when the target exits ("Process N finished with exit code X").
- Errors are shown in the Debug console as "Cannot attach to process N: …", never as a hang: the process is gone (checked before injecting and while waiting), access denied (an elevated or other user's process; restart PyIDE as administrator), Python older than 3.10 (debugpy 1.8's minimum), the injector failing (its last output lines) or running over 30 s, and the target not starting debugpy within 20 s (`PYIDE_ATTACH_TIMEOUT_MS`), e.g. a program blocked in one long native call, which runs injected code only when it executes Python again.
- Test: `verify/attach-process.mjs` (port 9130) checks the error wording as pure Node, then starts `counter.py` (a 0.2 s counting loop) outside the IDE, sets a breakpoint, opens the dialog with Ctrl+Alt+F5 (project process first, no sidecars, version shown, filtering), attaches with Enter, checks the hit, the counter in Variables, frames, evaluate, F9 to the next hit, F8, program output, detaches with Ctrl+F2 and checks the process is alive, attaches again (direct connect) and detaches with the Stop button, kills only that process tree, then attaches to a process that has just exited and to one blocked in `time.sleep(300)` (8 s timeout) and checks both messages and that no session is left.

## Appearance modes (Distraction-Free, Zen, Full Screen, Presentation)

- Zen Mode is Distraction-Free in full screen. Full Screen is only `BrowserWindow.setFullScreen` (`appearance-modes:setFullScreen(on)`, `appearance-modes:isFullScreen`). ## Vulnerable packages (OSV)

`renderer/features/vulnerabilities` (plugin `vulnerabilities`, depends on `packages`), `main/features/vulnerabilities.js` and the pure `main/packages/osv.js` flag packages with known vulnerabilities, like PyCharm's vulnerable dependency inspection, from the [OSV](https://osv.dev) database. Nothing extra is installed: the main process uses `fetch` against `https://api.osv.dev` (`POST /v1/querybatch` for every package@version in one request, then `GET /v1/vulns/{id}` for each advisory). `PYIDE_OSV_URL` replaces the base URL; `off` turns lookups off (only cached answers show, and the manual check reports it). `verify/lib.mjs` sets `off` for every suite, so tests never reach osv.dev; `verify/vulnerabilities.mjs` points it at a fake server.

- What is checked: the installed packages of the project interpreter (the Python Packages window's list) and, for each requirement of `ide.dependencies` (requirements*.txt, pyproject.toml, Pipfile), the version it stands for: an exact pin (`==1.0`, `===1.0`), else the version `uv.lock` / `poetry.lock` resolves, else the installed version when it satisfies the requirement. A range with no known version is not checked.
- Where it shows: in the Python Packages window a ⚠ on the row (`.pkg-vuln-icon`, `data-vulnerable` = count) and, for the selected package, the advisories (`#pkgVulns`: id linking to the ADVISORY reference or osv.dev, aliases such as the CVE, the database's severity label or the CVSS vector, the summary, the fixed versions) with "Upgrade to <version>" (`#pkgVulnUpgrade`), which runs the window's ordinary `pip install <name>==<version>`. The version is the first one above the installed one that none of its advisories affects, from the versions they name as fixed (OSV's range rules: `introduced`, `fixed`, `last_affected`, explicit `versions`). Requirement lines get a warning (problems source `vulnerabilities`, so also a Problems entry and a marker hover listing the advisories) and the quick fix "Upgrade to <version>" (Alt+Enter or the lightbulb), a Monaco edit that pins `==<version>` when the line pinned with `==`, otherwise sets `>=<version>` and keeps the upper bounds and `!=` clauses the version still meets, the extras and the marker. The fix is offered only while the line still holds the text that was checked, and not for Poetry or Pipfile tables, whose entries are not PEP 508 strings.
- When: after every package listing (`packagesListed`) and dependency check (`dependenciesChecked`), so also after installs, the interpreter changing and dependency files being edited. Answers are cached in `<userData>/vulnerabilities/osv-cache.json` for 24 hours per package@version and per advisory, so each is asked at most once a day, also across restarts; expired answers still show while offline. Check for Vulnerabilities (Find Action `CheckForVulnerabilities`, and the 🛡 button `data-action="checkVulnerabilities"` of the Python Packages window) asks again for everything. Errors (offline, timeout after 20 s, an HTTP error) never block anything: the window shows a quiet note (`#vulnStatus`, `data-kind="error"`) with Retry, and the IDE log a warning. A failed lookup carries `errorKind` (`network`, `timeout`, `server`), and the note shows a translated sentence for each ("Could not check for vulnerabilities: Cannot reach the vulnerability database (osv.dev). Check your internet connection or proxy settings."), with Node's message in its tooltip and the log; an unknown error still shows its message (`verify/tool-failures.mjs`).
- Trust: in Safe Mode (`ide.trusted === false`) nothing is sent automatically, and the note says so with a Check for Vulnerabilities button; cached answers still show. The request runs nothing from the project, but its content (package names, some of them possibly private, read from files the project ships) would leave the machine just because a folder was opened, which is what Safe Mode avoids; the manual check is the user's decision. The same rule lets the manual check run while the setting is off.
- Setting: `packages.vulnerabilityCheck` (Settings › Vulnerable Packages, default on). Off clears the marks and stops the automatic checks.
- `ide.packages` (packages plugin), the extension points this plugin uses: `list()`, `busy()`, `toolWindow`, `notes()` (a host under the window's search field), `install(spec)`, `select(name)`, `render()`, `decorateRow(fn(row, pkg))`, `addDetails(fn(pkg, {busy}) -> element | null)`, `addAction({icon, title, id, run})`. `ide.vulnerabilities`: `check({manual})`, `state()`. IPC `vulnerabilities:check({root, installed, files, lock, network, force})` and `vulnerabilities:clearCache`.
- Quick fix "Upgrade to x.y.z" (IPC `vulnerabilities:upgrade`, `upgradeSource` / `upgradeRequirement` in `osv.js`): re-reads the requirement from the editor (through `` continuation lines) and changes only its specifier, keeping name, extras, marker, comment, options and spacing. Clauses the fixed version satisfies stay (`~=`, `==X.*`, `<`, `!=`), a pin becomes `==fixed`, a lower bound becomes `>=fixed`, otherwise `,>=fixed` is added. No quick fix when a written clause excludes the fix (e.g. `~=3.1.0` with 3.2.25), on `--hash` lines, URL requirements, Pipfile and Poetry tables. The cache file is validated entry by entry on load and written atomically (temp file + rename).
- Test: `node verify/vulnerabilities.mjs --unit` runs only the pure-Node part (requirement rewrites, cache loader, IPC over a damaged cache). `verify/vulnerabilities.mjs` (ports 9220-9221 for CDP, 9228 for a fake OSV server in the test process, node `http`, which counts requests) builds pyide-vuln-demo 1.0 and 1.1 wheels offline as `verify/deps.mjs` does and installs 1.0 into a temp project venv; the fixture pins `pyide-vuln-demo==1.0`. It checks the squiggle, its message and hover, the Problems entry, the row icon and the details, that each package@version and advisory is asked once and a later listing or dependency check asks nothing, the quick fix rewriting the pin to `==1.1`, Upgrade installing the 1.1 wheel and clearing the marks, the server stopped (a note, no exception), the setting off (no requests), Safe Mode (no automatic request, the note's button asks once), and in Korean after a restart with the same user data: nothing is asked again, the manual check asks once, and the texts and the settings page are Korean.

## Split terminals

`renderer/features/terminal` splits a Terminal tab the way PyCharm's Terminal tool window does. A tab holds a tree of panes (a leaf is one pane, a split is `{dir: 'row'|'column', ratio, a, b}`, so splits nest), and each pane is its own PTY session (`pty:create`, unchanged in `main/features/terminal.js`).

- Split Right / Split Down: the tab's and the pane's context menus and the tool window toolbar; actions `Terminal.SplitRight`, `Terminal.SplitDown`, unbound by default as in PyCharm (menus and the toolbar tooltip show a user binding through `keyAction`). The new pane starts in the split pane's folder with the same shell (a Claude Code or installer pane splits into a plain shell). The folder is the one the pane started in, or the last one its shell reported with OSC 7 (`file://host/path`) or Windows Terminal's OSC 9;9 (`"path"`); PowerShell reports nothing unless the user's prompt prints it.
- Layout: the panes reuse the editor's `.split` / `.split-handle` classes. A divider keeps 80 px (side by side) or 40 px (stacked) on each side and resets to half on double-click; where a nested divider meets its parent's, the parent's takes the mouse. Every pane fits its own xterm to its size (`ide.util.observeSize` per pane, the fit addon), and xterm's resize reaches the PTY, so `$Host.UI.RawUI.WindowSize` / `mode con` follow the divider. A pane in a hidden tab keeps its size until it shows.
- Focus: clicking a pane, `Terminal.NextSplitter` / `Terminal.PreviousSplitter` (Next/Previous Terminal Split, unbound, in reading order of the tree, wrapping). The active pane has a 1px outline while the tab is split, and the tab title (and its rename) is the active pane's; a split tab shows its pane count.
- Closing: Close Session (pane menu, `Terminal.CloseSession`) closes one pane and gives its room to its neighbour; the last pane closes the tab; the tab's × and its menu's Close Tab close every pane. `exit` in a split pane closes it; a tab's only pane keeps its output with "Press Enter to close this tab", as before. Each close kills the pane's PTY (`pty:kill`: node-pty kills every process attached to the pane's console, so a running `ping` or `python` goes too). Closing the project, or opening another project in the window, closes all terminal tabs; if any session is still running, it first asks "Terminate Processes" through `ide.beforeProjectChange`, and Cancel keeps the project and every session. Installer sessions (`projectless`) are not tied to a project and keep running across a switch. A renderer reload (Trust Project) kills the window's sessions in main on its `did-navigate`; quitting kills the rest (`before-quit`, window `destroyed`).
- Folders from terminal output: OSC 9;9 and OSC 7 only set a pane's folder to a local drive path (OSC 7 only from an empty host, localhost or this computer's name); UNC and other network paths are ignored, and `pty:create` starts any non-local `cwd` in the home folder, so output can never make PyIDE open an SMB connection.
- Persistence: terminal tabs are not restored when a project reopens, so layouts are not either.
- Shells: the default shell is chosen in Settings › Terminal › Default shell (`terminal.shell`, from the shells `pty:shells` found). Windows PowerShell starts by its full path (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`), so a PATH without its folder does not matter. A shell that cannot be found answers `pty:create` with `{error: 'shellNotFound', shell, shellName, file}` (not an IPC error); the tab says "The terminal could not start: PowerShell 7 was not found (<file>)." and points to New Session with… (▾) and the setting. Each session's ConPTY input pipe, output pipe and output-reader thread are released when it ends (`releasePty(proc)` in `main/features/terminal.js`: @lydell/node-pty 1.1 never destroys the input socket, and keeps the output-reader worker of a shell that exits by itself). Tests: `verify/terminal-pipes.mjs` (ports 9284-9285, the main process over `--inspect`: 25 terminals closed from the tab and 25 ended by `exit`, PipeWrap and thread counts flat), `verify/env-failures.mjs` (a missing shell, the picker).
- `ide.terminal`: `sessions()` lists every pane (`{id, name, kind, exited, pid, cwd, tab}`), `tabs()` gives `{name, active, panes, layout}`, `split('right'|'down', id?)`, `focus(id)`, `close(id?)`; `text(id)`, `send(text, id)` and `active()` (now with `pid`) work per pane. Panes are `.term-pane[data-session=<id>]` around the old `.term-session`.
- Test: `verify/terminal-split.mjs` (ports 9210-9211; in CI) splits right from the toolbar and down from the pane menu (nested), checks each pane's own shell, folder and output, drags the divider and compares `$Host.UI.RawUI.WindowSize.Width` with xterm's columns, the minimum size, Next/Previous and click focus, a user binding in menus, the tooltip and inside the terminal, closing a pane, `exit`, closing the last pane and a tab, closing the project and quitting the app with a `ping` running in each pane (the shell PIDs and their child processes, from `Win32_Process`, must be gone), and the Korean menus and action names.

## Settings export and import

File › Manage IDE Settings › Import Settings… / Export Settings… (`ImportSettings`, `ExportSettings`; plugin `settings-sync`: `renderer/features/settings-sync`, `main/features/settings-sync.js`, `main/settings-sync/archive.js` and `unzip.js`) move the user's IDE-level state between computers as one `.zip`, as in PyCharm.

- Export: a dialog lists the categories with what each holds (all ticked; Recent projects list unticked; Scratch files unticked when the folder is over 20 MB; empty ones disabled), then the Save dialog (default `settings.zip` in the home folder). Import: the Open dialog, then the archive is checked and its categories are listed (ticked); Import backs up the current state to `<userData>/settings-backups/<yyyy-mm-dd_hh-mm-ss>.zip` (same format, every category except scratch files, which an import never overwrites), applies the chosen ones and offers Restart / Not Now (language and plugin state need a restart; the rest applies at once).
- Archive: `pyide-settings.json` (`{format: 1, product: 'PyIDE', version, created, categories: {id: {count}}}`), `settings/appearance.json`, `settings/code-style.json` (`{key: value}`), `keymap.json` (the `keymap.overrides` object), `live-templates.json` (`{custom, postfixDisabled}`), `plugins.json` (`{disabled}`), `database/sources.json` (`{version, sources}`), `scratches/<path>`, `recent-projects.json` (`{projects}`). Written with `main/diagnostics/zip.js` (deflate); read with `main/settings-sync/unzip.js`, a ~90-line reader (central directory, stored and deflate, CRC and size checks) that reads entries by name. `open()` refuses an archive before inflating anything when it has more than 5000 entries, when two entries share or overlap bytes (a ZIP bomb pointing many entries at one stream), or when declared sizes exceed the limits in `archive.js` `LIMITS` (archive 512 MB, 512 MB unpacked in total, 64 MB per entry, manifest 1 MB, each category JSON 16 MB, at most 1000 scratch files and 256 MB of scratches; export keeps to the same scratch limits). Entries are inflated asynchronously (`readAsync`, `maxOutputLength` = the declared size), and one import runs at a time. No ZIP library ships at run time (yauzl and unzipper are electron/electron-builder build dependencies), and the `tar` on PATH may be Git's GNU tar (see `zip.js`), so nothing was added to package.json.
- Refused, with a translated message and nothing changed (no backup either): a file that is not a zip or is damaged, a zip without `pyide-settings.json` or with an invalid one, a newer `format` ("exported by a newer PyIDE (version, format N). Update PyIDE…"), and any entry name that is absolute, has a drive letter, a backslash, a `.`/`..` segment, `:` (alternate data streams), a reserved device name or control characters (zip-slip). Unknown but safe entries are ignored. Every chosen entry is read and checked before anything is written; scratch files are written only under `<userData>/scratches` (resolved path checked again), with `wx`.
- Applying: settings keys merge (imported wins, the user's other keys stay); keymap overrides are replaced; live templates merge per abbreviation, imported wins (the result names the replaced ones; the backup holds the old ones), postfix switches are replaced; plugin state replaces `disabled` in `plugin-state.json` (other fields kept); data sources go through `ide.database.addDataSource` (same id: the local encrypted password is kept), or straight into `sources.json` when the Database plugin is disabled; scratch files are added, an identical file is skipped and a different one with the same name is kept as `name_1.ext`; recent projects merge by path (newest 15). Imported recent projects are not trusted (`trusted-projects.json` is never touched). The renderer applies settings.json keys, because it owns that file (`ide.settings`), and calls `ide.settings.flush()` before export and import so main reads the current file.
- IPC (`main/features/settings-sync.js`): `settings:chooseExportFile(title)` / `settings:chooseImportFile(title)` show the dialogs and remember the path returned; `settings:exportInfo()`, `settings:export(file, categories)`, `settings:inspect(file)`, `settings:import(file, categories, {databaseLoaded})` accept only a path the matching dialog returned in this session (otherwise `{ok: false, code: 'notChosen'}`). Errors are `{ok: false, code: notZip | noManifest | badManifest | newerFormat | unsafeEntry | badEntry | tooLarge | tooManyEntries | overlap | busy | readFailed | failed, detail, version?, format?, size?, limit?, count?}`. `PYIDE_SETTINGS_SYNC_DIALOG` (tests only) names a JSON file `{save?, open?}` read at each dialog instead of showing it.

What is exported. A settings.json key is classified by `classify()` in `main/settings-sync/archive.js`, on export and again on import (a crafted archive cannot set interpreter paths or the update feed): its own categories first, then never a key matching the diagnostics secret pattern (`SECRET_KEY`: password, token, api key, secret, credential…), never a per-project key (one holding a path: `[\/:]`), never the excluded keys below, never a key outside the preference groups, and never a value holding an absolute Windows path. A new feature's keys are exported only if their group prefix is in `PREFERENCE` there; add the prefix or an `EXCLUDED` entry when adding settings.

## GitHub (Share Project, Pull Requests)

`renderer/features/github` (plugin `github`, depends on `vcs`) and `main/features/github.js` work through the GitHub CLI, like PyCharm's GitHub plugin but without its own OAuth: gh holds the login. Git › GitHub has Share Project on GitHub… (`Github.Share.Project`) and View Pull Requests (`Github.View.Pull.Request`); no shortcuts.

- Finding gh: `PYIDE_GH` names the executable to use (`none` simulates a missing one); otherwise `where gh`, then the MSI, winget-links, scoop and Chocolatey locations, so a gh installed after PyIDE started is found by Refresh. `github:status` runs `gh --version` and `gh auth status` (account parsed from both the 2.40+ and older wording). A `.cmd`/`.bat` gh runs through `cmd.exe /d /s /c` with every argument quoted and its metacharacters escaped twice (cross-spawn's rule), so descriptions with `"`, `&`, `%`, `^`, `!` or Korean reach gh unchanged. gh runs with `GH_PROMPT_DISABLED`, no update notifier, no color, and a 60 s limit for reads (10 min for create/checkout).
- Trust: every channel refuses a project the user has not trusted (`main/trust.js`), and the renderer does not call them while `ide.trusted === false`; the tool window and Share explain that GitHub features are off in Safe Mode. Nothing runs gh until the tool window is shown or Share is used.
- Share Project on GitHub: needs gh logged in (else the dialog explains install or login), a repository with a commit (else it offers the Commit tool window, running `git init` first if needed), and no GitHub remote yet. The dialog asks for the repository name (folder name, made URL-safe), Private (on), remote (`origin`, or `github` when `origin` is taken) and description, then runs `gh repo create <name> --private|--public [--description <text>] --source <root> --remote <remote> --push`. Its output streams into the Git console (`ide.vcs.appendConsole`, added for this), and the notification shows the new URL. Names and remotes are validated on both sides.
- Pull Requests tool window (left, order 40): the state area explains a missing gh (Install GitHub CLI… opens the Install Manager's System Tools, where `system:gh` installs `GitHub.cli` with winget; a cli.github.com button), a logged-out gh (Log In in Terminal runs `gh auth login` in a PowerShell terminal session), and a project without a GitHub remote (Share button). Otherwise a filter (Open / Closed / Your pull requests: `gh pr list --json number,title,author,headRefName,baseRefName,state,isDraft,updatedAt,reviewDecision --limit 50 --state open|closed [--author @me]`) and the list (title, number, author, branches, time, Draft / review decision / Merged / Closed badges; keyboard via `ide.ui.listKeys`). Selecting one runs `gh pr view <n> --json title,body,author,commits,files,reviews,comments,statusCheckRollup,number,url,state,isDraft,baseRefName,headRefName,headRefOid` and shows the header ("{author} wants to merge {head} into {base}"), Open in Browser, Checkout, the description as plain text (never rendered: it is the author's Markdown), files changed with line counts, checks (check runs and commit statuses summarized as passed / failed / pending / skipped, each with a Details link), commits, reviews and comments.
- A changed file opens `ide.vcs.openTextDiff` of the head commit against its merge base with `<remote>/<base>` (else the local base branch), from the local repository only (`github:fileDiff`). When the head commit is not local the note says to use Checkout; nothing is fetched. Checkout (button or the list's context menu) is the only command that fetches: it saves all, puts a Before Checkout label in Local History, runs `gh pr checkout <n>` into the Git console and reloads like a branch checkout. Open in Browser and Details open only https URLs; `PYIDE_FAKE_OPEN_EXTERNAL=1` records them instead (`github:openedUrls`).

## Shelf (Shelve Changes, Unshelve)

PyCharm's shelf, in the vcs plugin (`renderer/features/vcs`, `main/features/git.js`, channels `git:shelve`, `git:shelves`, `git:unshelve`, `git:shelfDiff`, `git:shelfRename`, `git:shelfDelete`). Git › Shelve Changes… (action `ChangesView.Shelve`, also a Commit window toolbar button) lists the changed files with checkboxes, preselecting the files selected in the Commit window or else those ticked for commit, with a name (default "Changes from <date>") and "Keep changes in working tree" (off; remembered in `vcs.shelf.keep`). Whole files only: the Commit window has no per-hunk selection to reuse. The Commit tool window has Commit | Shelf tabs (`.vcs-ctab`; Git › Show Shelf, `Vcs.Show.Shelf`): shelves newest first with their file count and date, expanded to their files (status colors, Ctrl+click selects several, keyboard via `ide.ui.listKeys`, Delete deletes), double-click shows the shelved diff in the usual diff tab (a binary file says it cannot be shown), and Unshelve, Unshelve Selected Files, Rename… and Delete… (asks first) from the bar and the context menu. "Remove successfully applied files from the shelf" (`vcs.shelf.removeApplied`, default on) drops the files that came back, with or without conflicts; a shelf with no files left is deleted.

- Storage: `<userData>/shelf/<sha1 of the project folder's real path, lower-cased>/<shelf id>/changes.patch` plus `shelf.json` (`{name, time, branch, head, files: [{rel, orig?, status, binary, staged}]}`). Not `.idea/shelf` as in PyCharm: PyIDE has no `.idea`, and a patch inside the work tree would show up as a change, could be committed, and `git clean` would delete it.
- Shelving builds the patch in a private index (`GIT_INDEX_FILE` in a temp folder): `read-tree HEAD`, `add -A` of exactly the chosen paths (and a rename's old path), then `diff --cached --binary --full-index -M` with fixed prefixes and no external diff or textconv. So untracked files are new files, deletions and renames (staged or found by `-M`) are kept, binary files are base85, CR line ends stay content, and the user's own index is never touched. The patch is one `diff --git` section per file, in the order of `--name-status`, which is how a subset is applied later. Unless kept, the files are then rolled back only after `git apply -R --check` of the patch succeeds: paths in HEAD are restored (`restore --source=HEAD --staged --worktree`), the others are unstaged and deleted (and folders left empty). A file is deleted only when the patch holds all of it (a new file, or the new name of a rename whose old name is in HEAD); if git cannot say which paths are in HEAD, or any step fails, the rollback stops before touching anything and the shelf is kept. A file that was staged as new (or a staged rename) is staged again when it comes back.
- Unshelving applies to the work tree without the index (`git apply`, `--whitespace=nowarn`), all chosen sections at once when they apply cleanly, else each that does. Each remaining file goes through `git apply --3way` against the blob it was shelved from; that needs the index to match the work tree, so its current state is staged first and its old index entry is put back unless git left it unmerged. A conflicted file has markers and index stages 1-3, so the vcs-merge Conflicts dialog and merge tool resolve it like a conflicting unstash, and it stays on the shelf (only cleanly applied files are removed) so "Accept Yours" never loses the shelved change; a file that cannot be applied at all (for example deleted since) is reported with git's reason and stays on the shelf. With `core.autocrlf=true`, files git rewrites come back with git's checkout line ends, as with `git stash`.
- Test: `verify/shelve.mjs` (ports 9250-9252): a repository with modified, CRLF, binary, deleted, renamed, staged-new and untracked files; shelve a subset rolling back (work tree, open editor, the patch's contents, nothing in the repository), a shelved text, rename and binary diff, a second shelf kept in the work tree, Unshelve Selected Files (binary byte for byte, removed from the shelf), Unshelve all over a conflicting edit (Conflicts dialog, CRLF kept, Accept Theirs; staged-new staged again, untracked untracked), a file that cannot be applied staying on the shelf with the index untouched, rename with a Korean name, persistence across a restart, delete; then in Korean the dialog, tab, notifications, menu and confirmation without English leaks, the remove option off, and no missing translations.

## Periodic update checks and Report on GitHub

`renderer/features/updater` and `main/features/updater.js` check for updates again while PyIDE runs; `renderer/features/diagnostics`, `main/features/diagnostics.js` and `main/diagnostics/redact.js` (`redactPaths`) turn an internal error into a prefilled GitHub issue.

- Periodic checks: Settings › Updates › "Check for updates" (`updates.checkOnStartup`, now the switch for every automatic check) with On startup only / Daily / Weekly (`updates.checkInterval`, default `daily`). - Report on GitHub: the IDE Internal Errors details have Report on GitHub… for the selected error, and Help › Report a Problem… (`ReportProblem`) reports without one. `diagnostics:reportDraft({errorId, plugins, root})` builds the issue in main: a title from the error message, "What happened" for the user to fill in, the environment (PyIDE version and install kind, Windows edition and version, Electron and Chromium, the number of enabled plugins that are not bundled), the error's plugin, source, kind and stack, and the last 30 lines of the IDE log. ## Commit checks and auto-fetch

Commit checks (plugin `vcs-checks`: `renderer/features/vcs-checks`, `main/features/vcs-checks.js`; depends on `vcs`) are PyCharm's commit options: the gear after the Commit buttons (`#vcsCommitOptions`) opens a Before Commit popup with Reformat code, Optimize imports, Analyze code, Check TODO and Run tests: plus a run configuration of the project. They run before every commit, Commit and Commit and Push alike, through `ide.vcs.addBeforeCommit(fn)` (the vcs plugin calls each hook once the files and message are valid; `false` stops the commit; it saves all and refreshes afterwards, committing the same files) and show a progress strip after the buttons ("Analyzing code… 3/4", `#vcsChecksProgress`) whose Cancel stops the step in progress and the commit; the same run is an `ide.tasks` task when that API exists. Order: Optimize imports, Reformat code (imports first, so the reformat tidies what removing one leaves), Analyze code, Check TODO, Run tests.

- Optimize imports / Reformat code: the tooling plugin's `tooling:optimizeImports` and `tooling:format` (ruff, `tools.ruffLineLength`) on each Python file being committed and nothing else; an open document is edited as one undo step and saved, a closed file is rewritten in its own encoding. A file ruff cannot parse is left as it is (a warning lists it). Disabled without the tooling plugin.
- Analyze code: `vcs-checks:analyze` runs the bundled Pyright CLI (`node_modules/pyright/index.js --outputjson --pythonpath <project interpreter>`, as Node through Electron) on the committed Python files as saved, since the language server only analyzes open files; plus ruff's lint as the editor shows it (warnings; a syntax error is an error) while `tools.ruffOnSave` is on. When ruff cannot run (`tooling:check` answers `{error}`, for example a broken ruff.toml) the check warns once, "ruff could not check the files being committed" with ruff's error, instead of treating the files as clean; Pyright failing to run is reported the same way. Errors stop the commit with "Code analysis found problems…: N errors, M warnings" and Review / Commit Anyway / Cancel; warnings alone do not. Review opens a tab listing the problems by file (`#vcsChecksResults`, a row opens the file at its line). `vcs-checks:cancel` kills a run.
- Check TODO: TODO and FIXME comments (PyCharm's default patterns, after `#` or `//` by file type) on lines the changes add that the replaced lines did not already have (`ide.vcs.diffLines` against HEAD). Same dialog and Review.
- Run tests: the chosen configuration runs through `ide.run.runConfig`, as Run would start it; it failed when its test status says failed (`.tr-status[data-state]`) or, for another type, its tab ended failed. Review shows the Run window with that session. A missing configuration skips the check with a warning.
- Settings: `vcs.commitChecks.reformat`, `.optimizeImports`, `.analyze` (default on), `.todo` (default on), `.runTests` per IDE, as in PyCharm; `vcs.commitChecks.testConfig:<project>` per project (a run configuration id). Choosing a configuration turns Run tests on. `ide.vcsChecks`: `checks()`, `testConfig()`, `running()`, `cancel()`, `openOptions()`. Other vcs extension points added: `ide.vcs.addCommitOption(node)`, `committing()`.

Auto-fetch (vcs plugin and `main/features/git.js`): every `vcs.autoFetchMinutes` minutes (default 10, fractions allowed, 0 = off; Settings › Git) the renderer asks `git:backgroundFetch`, first within 20 s of opening the project. Main runs `git fetch --all --prune --quiet --no-recurse-submodules` with `gc.auto=0` and `maintenance.auto=false` only when the project is trusted, is a repository with remotes, no IDE git operation is running for it (every `git:` channel that is not a read counts; push and pull wait for a fetch in flight, since two fetches writing remote refs fail on ref locks) and no `index.lock` is held. It never prompts: `GIT_TERMINAL_PROMPT=0`, empty `GIT_ASKPASS`/`SSH_ASKPASS` and `-c core.askPass=` (no askpass program, including one the user configured), `GCM_INTERACTIVE=never` and `-c credential.interactive=never` (credential helpers answer from their stores only; git then fails with "unable to get password from user"), `ssh -o BatchMode=yes` unless the user set an ssh command, and a 120 s limit (`PYIDE_GIT_FETCH_TIMEOUT_MS`). A failure goes to the IDE log (`#git`) only, and the next try waits twice as long each time, up to an hour; a success resets it and refreshes the status. A busy repository is tried again within 30 s. The toolbar shows the current branch's incoming and outgoing commits after the branch widget (`#vcsSync`, "↓3 ↑1", hidden when both are 0 or there is no upstream), with a tooltip (counts, upstream, last fetch) and a menu: Update Project…, Push… (when ahead), Fetch (a fetch the user asked for reports its errors). `ide.vcs.autoFetch`: `state()` (`{attempts, failures, skipped, lastFetch, lastError, nextDelay, running}`), `now()`.

## Before launch tasks and File Watchers

Before launch (run plugin, `renderer/features/run/index.js` + `main/features/run.js`), PyCharm's "Before launch" list in Run/Debug Configurations:

- A configuration's `beforeLaunch` is `[{kind: 'config', id} | {kind: 'tool', name?, program, args?, cwd?}]`, kept in the configuration JSON (`runConfigs:<project>` in the user's settings, never in the project). Configurations saved before the field existed have none; malformed entries are dropped when the project opens. The form's Before launch section adds (＋: Run Another Configuration, listing the other configurations, or Run External Tool), removes, and moves tasks up and down; a tool's Name, Program, Arguments and Working directory are edited below the list. "Save all files" stays the `autosave.beforeRun` setting (saves before every launch), and Activate tool window is not offered.
- `runConfig` and `debugConfig` (Alt+Shift+F9, gutter Debug, frameworks, scratches) run the tasks in order first. Run Another Configuration runs it in its own Run tab (with its own before launch tasks) and waits for its process to exit; Run External Tool runs in a Run tab named after the tool, with the command line and output there (`run:startTool`, the tab's Rerun runs the tool again). A non-zero exit, a Stop, a missing configuration, a program that cannot start or a missing working directory stops the launch: later tasks and the configuration do not run, and an error notification ("'Main' was not started", the task and the exit code) is posted. Progress is an `ide.tasks` background task ("Before launch: 'Main'", the running task as its text; cancelling it stops the running task). Run or Debug pressed again while a configuration's tasks run starts them over: `runBeforeLaunch` registers the newest launch of each configuration, and the earlier launch ends quietly when its current task returns (the newer launch reuses that task's Run tab and stops it), with no "was not started" notification; a dependency configuration replaced the same way is handled alike (`verify/run-debug-edges.mjs`).
- Cycles (A before B before A, or longer) are refused when added in the dialog (an error under the list, nothing added), on OK (the dialog stays open on the configuration in the cycle), and at launch (a hand-edited settings file: notification naming the cycle, nothing runs).
- Sessions: `session.finished` resolves with the exit code of the session's current run (-1 when it did not start, was replaced by a rerun or the tab closed); `exited(id, code)` takes the code (a type that leaves it out counts as success, a killed process, `null`, as failure). New `ide.run` members: `runBeforeLaunch(cfg)`, `findCycle(id, configs)`, `outputSession(key, title)` (a Run tab that is not a configuration's, kept with its console), `show(session)`, `notifyError(title, text)`.
- Macros (main/features/run.js `expandMacros`, shared with File Watchers), written `$Name$` or `${Name}`, case-insensitive, unknown ones left as written: `ProjectDir` (`ProjectFileDir`), `ProjectName`, `FilePath`, `FileName`, `FileNameWithoutExtension`, `FileNameWithoutAllExtensions`, `FileExt`, `FileDir`, `FileRelativePath`, `FileDirRelativeToProjectRoot`, `FileParentDir`, `PyInterpreterPath`, `PyInterpreterDirectory`. For before launch tools the file is the active editor's. Arguments are split like the script parameters (quotes group) before expansion, so a path with spaces stays one argument. A bare program name is looked up in the absolute PATH folders with PATHEXT (never the working folder); a `.cmd`/`.bat` (npm shims such as `sass.cmd`) runs through `cmd.exe /d /s /c`: arguments are quoted for the C runtime and their cmd metacharacters escaped once, or twice for npm shims (`node_modules.bin`, or a cmd-shim forwarding `%*`, `isNpmShim`), with `NoDefaultCurrentDirectoryInExePath=1` so cmd never runs a program from the project folder in place of one on PATH. Before launch tools, like File Watchers, are refused in a project that is not trusted. A tool's working directory defaults to the project folder. My Workspace's .bat launchers (`workspace:start`) and launch.json programs that resolve to a `.cmd`/`.bat` go through the same `toolCommand` (cmd metacharacters in the path escaped, no `call`, so a project path holding `&`, `^` or `%` works); a .bat's extra arguments are passed as typed (cmd syntax), and a bare launch.json program name is resolved on PATH with PATHEXT (`resolveProgram`), so `npm` runs `npm.cmd` with the npm-shim escaping and an .exe is spawned directly. ## Runtime performance (0.2.4)

Measured with CDP (Performance.getMetrics, Profiler, heap snapshots) and per-process CPU (Win32_Process) on a 2,000-line Python file and perf.mjs's 20,000-file project; fixes and their check in `verify/perf-runtime.mjs` (ports 9580-9581, numbers in `verify/out/perf-runtime/results.json`; not in CI, like perf.mjs and soak.mjs, since it times things).

- Inlay hints asked Pyright for a signatureHelp per visible call after every pause in typing. Pyright 1.1.406's signatureHelp also looks up documentation, which for an overloaded builtin takes seconds every time (`open(`: 5-7 s), and Pyright answers one request at a time, so typing in a large file kept it at 1.5 cores and completion waited ~10 s behind queued hint requests (19 s of hint work after the last key). Now the plugin asks for the callee's hover first (quick; it prints the signature with its parameter names) and asks signatureHelp once per printed signature and argument count, reusing the names at every call with the same signature, in any file and after edits; requests go at most two at a time, and a provide call Monaco cancels drops its queued requests and cancels the sent ones. ## Class diagrams (Show Diagram)

`renderer/features/diagrams` (plugin `diagrams`), `main/features/diagrams.js` and `main/diagrams/model.js` add PyCharm Professional's Diagrams › Show Diagram for Python (action `ShowUmlDiagram`, Ctrl+Alt+Shift+U): Show Diagram in the project tree's context menu on a `.py` file or a folder/package, and in the Python editor's context menu, where the class at the caret shows with its bases and subclasses (all levels) and the classes it is associated with in either direction (no class at the caret: the file). The shortcut takes the class at the caret in an editor, the selected tree row while the tree has focus, else the current Python file.

- Model: `renderer/features/diagrams/python/diagram_model.py` runs in the project interpreter (a local one when the project interpreter is remote) with `-I` and reads files with `ast` only; user code is never imported or run. Per class: bases, methods (visibility from leading underscores, static, class, property with its setter folded in, abstract, async, overloads folded), fields (class attributes, annotated attributes, `ClassVar`, `self.x = …` / `self.x: T = …` in `__init__`/`__post_init__`, taking a parameter's annotation for `self.x = x`), dataclass and attrs fields, Enum members, nested classes, and the class names in attribute annotations (strings and `X | None` too; inside `list[…]`, `Dict[…]`… they count as to-many). `model.js` resolves names as Python binds them: classes of the module, `import a.b`, `import a.b as x`, `from m import n as x` (absolute and relative), `from m import *`, module-level aliases and re-exports through `__init__.py`. A file is known by its package-chain module name and by its path from the project root and from `<root>/src` (src layout, namespace packages). Modules a scope's classes import from outside the scope are parsed on demand so their bases resolve (shown classes' project bases are included). Parsed files are cached per path, mtime and size for the session; unsaved editor text is read instead of the file. The walk skips caches, `node_modules`, virtual environments (`pyvenv.cfg`, `conda-meta`, `venv`/`.venv`/`env`) and dot folders and stops at `diagrams.maxFiles` (default 5000) files. Files with syntax errors are skipped and counted in the status line (their messages in the ⚠ tooltip). Parsing runs as an `ide.tasks` task ("Building class diagram", files done/total); Cancel kills the Python process.
- View: an editor tab with an SVG diagram. Class boxes have a header («enum», «dataclass», «abstract» or «protocol», the name in italics when abstract, the module) and field and method sections with PyCharm-like icons (f field, e enum member, m method, s static, c class method, p property; static members underlined, abstract methods italic, `#`/`−` for protected/private). Toolbar toggles Fields, Methods and Private (settings `diagrams.showFields`, `diagrams.showMethods`, `diagrams.showPrivate`), zoom in/out, 1:1, Fit, Add Class… (a search over the project's classes; the first use parses the whole project, from the cache), Export SVG and PNG, Refresh. Inheritance arrows have hollow triangles and are routed orthogonally into the base's bottom centre; associations are straight lines with an open arrow, the attribute names and `*` for to-many. Clicking a class selects it and highlights its relations (others dimmed); double-click or Enter opens the class in the editor; Delete removes it (and its context menu has Jump to Source and Remove from Diagram). Pan by dragging the background, middle button, Space+drag or the wheel (Shift+wheel horizontally); Ctrl+wheel zooms around the cursor, `+`/`-` zoom. Saving a Python file under a diagram's scope refreshes it, keeping added and removed classes.
- Layout (`ide.diagrams.layout(nodes, edges)`, no library): per inheritance component, longest-path layering (a class without bases then moves down next to its highest subclass), dummy nodes on long edges, 24 alternating barycenter sweeps keeping the order with the fewest crossings (counted with a Fenwick tree), then x coordinates by repeated least-squares placement towards the neighbours' mean under the order and gap constraints (pool-adjacent-violators); components and single classes are shelf-packed into rows. 300 classes lay out in ~10 ms (~30 ms with text measuring) and draw in ~70 ms.
- Panning moves a composited wrapper (`.dg-layer`), not the `<svg>`: a transform on the `<svg>` itself made Chrome lay out all ~10,000 SVG elements on every move (~30 ms per frame). Zoom resizes the `<svg>` (crisp text at every scale).
- Theme colours are the `--dg-*` variables in `style.css` (Dark and Light); the SVG rules live in `index.js` (`svgCss`), injected into the page and, for an export, copied with the current theme's values. SVG export is a standalone file with its own `<style>`; PNG export draws that SVG on a canvas at twice the size (capped at 16,000 px per side and 120 MP). Both go through a save dialog, and `diagrams:write` writes only a path that dialog returned in this session (like Export Settings); `PYIDE_DIAGRAMS_SAVE_DIR` (tests) answers `<dir>/<name>` without it and also allows files directly in that folder. The diagram itself is marked `data-user-text` (class names are user data).
- `ide.diagrams`: `show()`, `showPaths(paths)`, `showAt(path, line)`, `get(tabId?)`, `state(tabId?)` (classes with boxes, routed edges, options, view, timing, parse stats), `layout`, `measure`, `exportSvg(file?)`, `exportPng(file?)`, `addClass(id?)`, `findClass(qualname)`, `slowMs` (tests: delays each parsed file so a run can be cancelled).
- Test: `verify/diagrams.mjs` (ports 9040-9042; in CI; fixture `verify/fixtures/diagrams`): pure Node resolution checks (aliases, star imports, re-exports, src layout names); A: cancelling a parse from the task, the tree's Show Diagram with its shortcut hint, classes, inheritance across modules (relative imports, `import a.b`, aliases, `TYPE_CHECKING`, src layout, multiple inheritance), associations and to-many, stereotypes, members and their marks, the syntax-error file, that `danger.py` never ran, no overlaps and bases above subclasses, toggles, selection highlight, double-click navigation, Delete, Add Class… (another source root, a package re-export), Ctrl+wheel, Fit, pan, the editor action and Ctrl+Alt+Shift+U, the cache (second run parses nothing, a changed file alone is parsed again), unsaved text, SVG content and colours, PNG size, the Light theme; B: a generated 300-class project (layout under 1 s, no overlaps, bases above subclasses, pan frame times at the fitted scale and at 1:1, zoom and relayout times); C: Korean toolbar, status, menu and no missing translations. `DIAGRAMS_ONLY=fixture|big|ko` runs one part.

## File compare and line separators

File compare (plugin `compare`, `renderer/features/compare` + `main/features/compare.js`), as in PyCharm:

- Entry points: select two files in the Project tool window (Ctrl+click adds a row to the selection or takes it out; a plain click or arrow key selects one row again) and use the context menu's Compare Files or Ctrl+D; Compare With… (`CompareTwoFiles`, View menu, Ctrl+D in the tree, the tree menu of one file) compares the selected or current file with a file picked from the project (or Browse…); Compare with Clipboard (`CompareClipboardWithSelection`, View menu and the editor's context menu) compares the clipboard with the whole file, or with the selection when there is one; Compare with Branch… (`Git.CompareWithBranch`, Git menu, and Git: Compare with Branch… in the tree menu of a file) picks a local or remote branch, one of the last 50 commits or any revision typed into the picker (a tag, `HEAD~2`) and shows `git show <rev>:<file>` (an empty side titled "does not exist there" when the file is missing in it).

It opens at the first difference with the keyboard in the right side. The left side is a read-only snapshot. The right side, when it is a file, is that file's own document: the tab holds it through `ide.openCustomTab({doc})`, so edits show the modified mark, Save All (Ctrl+S) writes them with the file's encoding and line separator, the status bar shows its encoding and separator, and closing the tab with unsaved edits asks first. - A compare tab's path is only its title: Open in New Window / Move to New Window (also from Find Action), Copy Path, Select in Project View and Show in Explorer act only on file and viewer tabs. Deleting a file closes every tab holding its document in every window, compare tabs included, so nothing saves it back; a renamed file's modified document shown only in a compare tab gets a file tab at the new path, so its text is not lost. A document loaded for a comparison that was opened meanwhile is released (`ide.releaseDocument(doc)`). While the debugger is suspended, F7 in a focused diff tab is still Next Difference (`ide.compare.diffFocused()`).
- Binary files, files over 5 MB (`ide.compare.MAX_DIFF_BYTES`) and unreadable files open a message tab that says why, and for two files whether their bytes are the same (`compare:sameBytes`, read in 1 MB slices).
- Core hooks: `ide.loadDocument(path)` (a document without a tab; hand it to `ide.openCustomTab({doc})` at once), `ide.openCustomTab({..., doc})`, `ide.selectedTreeEntries()` and tree actions' `when(entry, selection)` / `run(entry, selection)`. `ide.compare`: `files(left, right)`, `with(path)`, `clipboard(editor)`, `branch(path, rev?)`, `view(tab?)` -> `{diff, go(dir), count(), ready(), setUnified(on)}`.

Line separators (core `renderer/core/editors.js`; the status bar widget is the `line-separators` plugin):

- A document keeps its file's separator: `doc.lineSeparator` (`'\n'`, `'\r\n'` or `'\r'`, the most frequent one; ties go to LF) and `doc.mixedSeparators`. Monaco knows only LF and CRLF and normalizes a model to one of them, so a CR file's model is CRLF and saving turns it back (`ide.lineSeparators.diskText(doc)`); a mixed file is saved with its main separator everywhere. Reload from disk, Load File System Changes and Reload in another encoding detect it again (event `lineSeparatorChanged(doc)`). Before this, saving already kept CRLF (Monaco's model kept the file's majority EOL and `getValue()` used it), but CR files were saved as CRLF and a file without line breaks got LF.
- New files: Settings › Editor › Code Style › Line separator for new files (`editor.lineSeparator`: `system` (CRLF on Windows), `lf`, `crlf`; exported with the code style settings). New Python File and the file templates write their text with it (`ide.lineSeparators.forNewFile(text)`), and a file without any line break (an empty new file) uses it too.
- The widget (`#statusLineSeparator`) sits between the caret position and the encoding and always shows for a tab with a document, like the encoding (it is not an ordered `#statusItems` widget, so a crowded status bar never hides it). Its tooltip names the separator and says when the file has mixed ones; its menu (`#lineSeparatorMenu`) converts the whole file to LF, CRLF or CR (also the actions `ConvertToUnixLineSeparators`, `ConvertToWindowsLineSeparators`, `ConvertToMacLineSeparators`). A conversion is one undo step and marks the file modified; CR <-> CRLF, which changes nothing in Monaco's model, does it by rewriting the first character. The plugin remembers the separator per model version, so Undo and Redo bring the right one back (Monaco reports an undone EOL change without `isUndoing`). `ide.lineSeparators`: `detect(text)`, `newFile()`, `forNewFile(text)`, `diskText(doc)`, `convert(doc, sep)`, `name(sep)`.

## Database Export Data and number fidelity

Export Data… (PyCharm's data extractors; plugin `database`: `renderer/features/database/export.js`, `main/db/export.js`, IPC in `main/features/database.js`) writes a query result or a whole table to a file. It is in the console's result bar (`.db-export`), the result grid's context menu, the context menu of a table or view in the Database tool window, and Find Action (`Database.ExportData`, no shortcut).

- Formats: CSV (value separator `,` `;` Tab `|`, column header, quote values when needed / always / never), TSV (CSV with Tab), JSON (array of objects, or JSON Lines), SQL INSERT statements (one per row; the table's own quoted name, or a typed name used as written, `MY_TABLE` for a query), Markdown table (`|` escaped, line breaks as `<br>`), and Excel `.xlsx`. Text formats are written in UTF-8, UTF-8 with BOM (Excel opens UTF-8 CSV correctly only with it) or UTF-16 LE with BOM. CSV/TSV use CRLF; NULL is an empty field (an empty string is `""` when quoted), blobs are `0x…` hex in CSV, Markdown and xlsx, `{"$base64": "…"}` in JSON, and the dialect's literal in SQL (`kind.sqlDialect`: postgres `'\x..'::bytea`, mysql `X'..'`, mssql `0x..` with `N'…'` strings, oracle `HEXTORAW('..')`, duckdb `'\xAA'::BLOB`, clickhouse `unhex('..')`, standard `X'..'`); numbers keep the database's text everywhere (`{$number}`), bigints stay exact (SQL Server DECIMAL/MONEY only to 15 digits, a tedious limit). The options are remembered in `database.export`.
- `.xlsx` is written by `main/db/export.js` itself, no dependency: a ZIP written front to back (small parts deflated in memory, the sheet deflated as it streams, with a data descriptor), `[Content_Types].xml`, `_rels/.rels`, `xl/workbook.xml` (sheet named after the table), its relationships, `xl/styles.xml` (bold header) and `xl/worksheets/sheet1.xml` with inline strings (no shared string table, so rows stream). Numbers Excel holds exactly (15 significant digits) are numbers; bigger integers are text; booleans are booleans; NULL is no cell; text is cut at 32,767 characters and rows at 1,048,576 (the notification says so).
- What runs: a table exports `SELECT * FROM <qualified name>` (with a `COUNT(*)` first for the progress bar); a console result runs again (read-only) only when `isReadOnlyStatement` (renderer/features/database/export.js) proves it only reads: plain `SELECT`/`WITH`/`VALUES`/`TABLE` with no `INTO`, data-modifying CTE, `FOR UPDATE`/`LOCK`, sequence use, known side-effecting functions or extra statements; `EXPLAIN` without `ANALYZE`; `SHOW`/`DESCRIBE`; reading PRAGMAs (comments and strings are removed first). Otherwise, when the grid holds every row they are exported; else a dialog asks: Export Shown Rows (default), Run and Export, or Cancel. MongoDB and Redis results export the rows the grid holds.
- Streaming: every SQL kind exports through a driver cursor (`adapter.cursor(sql, {readOnly})`, helpers in `main/db/cursors.js`), 1000 rows at a time, each batch written before the next is read, so a million-row table never sits in memory and every row is read exactly once in the statement's own order: SQLite `stmt.iterate()` on its worker; PostgreSQL/CockroachDB a `DECLARE … NO SCROLL CURSOR` + `FETCH` inside `BEGIN TRANSACTION READ ONLY` (a statement that cannot be declared, like `SHOW`, runs whole, capped at 1,000,000 rows and reported as `capped`); MySQL/MariaDB query events with pause/resume in `START TRANSACTION READ ONLY`; SQL Server `request.stream` with pause/resume; Oracle `resultSet` + `getRows` in a read-only transaction; DuckDB `prepared.stream()`; ClickHouse the HTTP response stream. Network kinds use a connection of their own (so the export cannot see the console's session state such as temp tables), push drivers are paused with at most ~2000 rows waiting, and Cancel closes the cursor at once (`db:exportCancel`). A kind without a cursor answers `EXPORT_UNSUPPORTED`. Errors cross IPC with a `code` (`NO_ROWS`, `NOTHING_TO_EXPORT`, `FILE_NOT_CHOSEN`, `UNKNOWN_FORMAT`, `EXPORT_UNSUPPORTED`) that the renderer translates. The file is written as `<name>.pyide-export` next to the target and renamed at the end; a cancelled or failed export removes it and leaves an existing file alone.
- Progress: an `ide.tasks` task "Exporting data to <file>" with "N of M rows" (a fraction for tables) and Cancel (`db:exportCancel`); then an `ok` notification with Show in Explorer, or an error notification.
- The Save dialog runs in main (`db:chooseExportFile({title, name, format})`, default `<Documents>/<name>.<ext>`), and `db:export({job, sourceId, format, options, file, table? | sql? | columns+rows?})` writes only a path that dialog returned in this session, like Export Settings. `PYIDE_DB_EXPORT_DIALOG` (tests only) names a JSON file `{save}` read at each dialog instead of showing it.
- Number fidelity: SQLite rows are read with BigInts, so a JS number is always a REAL. A REAL JS would print differently (2.0 as `2`, 1e20 as `100000000000000000000`, infinities) and an INTEGER past 2^53 now reach the renderer as `{$number: '2.0'}` / `{$number: '9007199254740993'}` (`fidelity()` in `main/db/kinds/sqlite.js`); the grid shows them right-aligned as numbers (`ide.database.cellText(v)`, `ide.database.isNumber(v)`), and Copy as CSV/TSV and every export use that text. `ide.database.query` results may therefore hold `{$number}` cells.

## Check RegExp

Plugin `regex-check` (`renderer/features/regex-check`, `main/features/regex-check.js`, `renderer/features/regex-check/regex_check.py`) is PyCharm's Check RegExp intention for Python.

- Where: on the pattern string literal of `re.compile`, `re.search`, `re.match`, `re.fullmatch`, `re.findall`, `re.finditer`, `re.sub`, `re.subn` or `re.split` (first argument or `pattern=`; raw, bytes and triple-quoted literals; not f-strings), Alt+Enter (lsp's Show Context Actions) lists Check RegExp. The character a syntax error points at is marked in the pattern line and in the editor. Esc (handled before the global keymap) closes it and returns to the editor; so do a click outside, an edit, or another tab.
- Python semantics: patterns are evaluated by `regex_check.py` in a local interpreter (the project's, or the first local one when the project's is remote), started with `-I -X utf8` so nothing in the project shadows `re`; JSON lines over stdio with non-ASCII escaped. The literal is decoded with `ast.literal_eval`, so escapes in non-raw strings and bytes patterns are exactly Python's; spans come back in UTF-16 units (Korean, emoji). Python-only syntax such as `(?P<name>…)`, `(?P=name)`, possessive quantifiers and atomic groups works. A check running longer than 3 s (catastrophic backtracking; `PYIDE_REGEX_TIMEOUT_MS` overrides) stops the helper and says so; the next check starts a new one. The helper also stops when the project closes or another opens and when the interpreter becomes another one (`regex-check:stop`), so a venv's python.exe does not stay locked; `regex-check:helperPid` (tests) gives its process id. At most 1000 matches are listed.
- Syntax colors: in Python editors, those pattern literals get decorations for groups, character classes, escapes, quantifiers, anchors, alternation and (with `re.X` or `(?x)`) comments (`rx-*` classes, light and dark colors). Non-raw literals are mapped through their escapes, so `"\\d"` colors as `\d`. Files without an `re.<function>(` call are not scanned.

A language server that just started answers references before it has listed the project's files (too few usages), so counting starts after its first diagnostics (`lsp:diagnostics`; or after 15 s). Files with more than 300 declarations get lenses only within 200 lines of the view (Monaco moves every lens on each keystroke), and the window follows scrolling. Authors come from one `git blame --porcelain --contents` (the vcs plugin's `git:blame` channel) per file, HEAD and saved text, for files in view: it reruns after a save or when HEAD moves (vcs emits `vcsHeadChanged({root, head})`), never while typing, never in an untrusted project (Safe Mode), and a file Git does not track simply has no authors. `ide.codeVision`: `symbols(model)`, `lenses(model)` (`[{line, kind: 'usages'|'authors'|'pending', title, key}]`), `stats()` (`references`, `cancelled`, `blames`, `runs`, `running`, `scheduled`), `refresh()`, `showUsages(arg)`, `showAuthors(arg)`. `verify/i18n-lib.mjs` skips `.codelens-decoration` in `englishLeaks` (author names are user data).

## Semantic highlighting and Type Hierarchy

Pyright 1.1.406 answers neither `textDocument/semanticTokens` nor `textDocument/prepareTypeHierarchy`. - Diagnostics: with basedpyright's own default rule set the fixtures got many new reports (lsp +5, breadcrumbs 0 → 26, refactor 0 → 59). With `typeCheckingMode: standard` sent in the `basedpyright.analysis` section the 16 fixture folders matched Pyright, except that unused-name hints carry a rule code and two Flask route functions are no longer "not accessed".

Instances of classes it can see are followed through constructor calls, annotations and return annotations; an attribute of a value of unknown type is a method when called and a property otherwise. It runs in the project interpreter, else the newest other local interpreter (any Python 3.8+; remote interpreters are skipped; one that cannot start is skipped until the interpreter list changes), isolated (`-I -X utf8 -B`: nothing on PYTHONPATH, in the user site-packages or next to the script can shadow what it imports; PYTHONPATH and the user site-packages are still searched when it reads modules), and stops when the project closes or another opens and on an interpreter change. A file that does not parse (typing in progress) keeps its last colors, moved with the edits. ## Visual Scripting (`*.pyflow`)

`renderer/features/visual-script` (plugin `visual-script`, depends on `run`; main module
`main/features/visual-script.js`) opens `*.pyflow` files as a Blueprint-style node graph that turns into readable
Python and runs like a script. `model.js` owns the file format and pure edit helpers, `nodes.js` the node types,
`codegen.js` the generator and `editor.js` the canvas; all four add to `window.PyideVisualScript` (`VS`), and
`index.js` loads them in that order, registers the `visual-script` text viewer and connects the graph to the IDE.

- File format (`model.js`): `{format: 1, nodes: [{id, type, x, y, props?, inputs?}], links: [{from: {node, pin}, to:
  {node, pin}}]}`, serialized deterministically (2-space indent, fixed key order, nodes by id number, links by
  from/to, defaults left out, unknown keys kept, final newline) so diffs stay readable; `VS.parse` throws readable
  errors with line and column, and an empty file is a new graph with one Start. A node id is letters A-Z and a-z,
  digits and _ only (the generated code names its locals after it); any other id is a parse error. The edit helpers (`addNode`,
  `removeNodes`, `moveNodes`, `setProp`, `setInputLiteral`, `connect`, `disconnect`, `disconnectAll`, `duplicate`,
  `pasteNodes`) return a new graph and never mutate; `connect` refuses incompatible types and cycles through
  `VS.lastError`.
- Node types (`nodes.js`): the registry (`VS.registerNodeType`, `nodeTypes`, `nodeType`, `pinsOf(node, graph)`) and the
  built-in library: Flow (Start, If, While, For Range, For Each, Break, Continue), Variables, Values, Math, Text (Join,
  conversions, Format Text), Input/Output (Print, Ask User), Lists, Functions (Define Function, Return, Call Function),
  Python (Call Python, Python Expression, Python Code) and Comment. Data types are any, number, int, string, bool,
  list, dict, none; `any` connects to everything and `int` to `number`. Pins a type makes from the node (Format Text
  fields, parameters) are user names and are never translated.
- Code (`codegen.js`, `VS.compile(graph, {fileName}) -> {code, map, errors}`): one statement per exec node under
  `def main():` and one `def` per Define Function, pure nodes inlined with only the parentheses Python needs,
  exec-node outputs in locals such as `answer_n7`, and `map[line]` -> node id for every generated line. Set Variable
  names are script variables (Blueprint's graph variables): a `def` that stores one (Set Variable, or a Python Code
  input or output of that name) declares it `global` after its `def` line, any function reads it, and a function
  parameter of the same name stays local. A value wired from a step must come from one that always runs before its
  consumer in the same function, earlier in an enclosing block (a loop's index and item only inside its body,
  `outputScope: 'body'`; a parameter anywhere in its function); otherwise the consumer's input pin gets an error that
  names the step and suggests Set Variable. Errors (no or two Start nodes, a required input left empty, a cycle,
  incompatible wires, an unset variable, an unknown function, invalid names, a value from a step that does not always
  run first, a function and a variable with the same name, Break/Continue outside a loop, Return outside a function)
  still produce code where the node in error raises `RuntimeError`; unreachable steps are a warning. Python Code keeps
  lines that start inside a string exactly (no re-indent, no tab expansion; `c.rawLine`). An Any field keeps a number
  with a leading zero or more than 15 integer digits as the text typed (`01012345678`); an integer a double cannot hold
  in a Number or Integer field is stored as its digits and written as typed. Text from the file reaches the code only
  validated: node ids and stored parameter names must be identifiers, a stored default is pasted only when it is a
  plain literal (`VS.isPythonLiteral`; otherwise that argument becomes required), and a Format Text spec cannot hold
  `{`. Python Code and Python Expression stay the visible escape hatch.
- The tab (`editor.js`): a `text: true` viewer over the file's document, and the document is the only state: every user
  operation (a drag, a wire, a literal, a paste) is one edit between undo stack marks, so dirty state, Ctrl+S, close
  prompts, Local History, crash recovery and Open as Text come from the core, and Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z on the
  canvas are the document's undo and redo. Another change of the document is parsed and drawn again; invalid JSON dims
  the canvas and shows the error with Open as Text. HTML nodes over an SVG layer of cubic wires on a 16 px grid; exec
  pins are triangles, data pins circles coloured by type (`--vs-type-*`), headers tinted by category (`--vs-cat-*`);
  inline literal fields and props in the node body; comments are notes behind nodes. Pan with the middle or right
  button or Space+drag, wheel zoom 25% to 200%, Ctrl+0, Fit. The first open fits the graph, never above 100%, and a
  graph that fits at 100% stays at 100%. The view is kept per file in `visualScript.view`.
- Editing: double-click, Tab or right-click › Add Node… opens the palette (search by English or Korean title and
  keywords; a whole title first, then a whole keyword or Python name, then a title's start, then any match, ties in
  category order: 입력 and input put Ask User first); a wire dropped on empty space offers only the types that fit and wires the pick. Drag
  between pins to connect (an incompatible pin turns the wire red and the status line says why), Alt+click a wire or
  pin to delete its wires, click / Shift / Ctrl / box selection, drag to move (16 px snap, Alt for none), Delete,
  Ctrl+C / Ctrl+X / Ctrl+V (JSON as `application/x-pyide-pyflow` and text), Ctrl+D, Ctrl+A. These keys are the
  canvas's own and fire only while it has focus. Problems are compiled 300 ms after each change: red outline, badge,
  and "No problems" / "N problems" in the status line (click: select the first). A field commits when it is left;
  an IDE shortcut pressed while typing (Ctrl+S, Ctrl+F4, Shift+F10) commits it first and keeps the keyboard in it with
  the same selection, so Ctrl+F4 asks to save the typed text. Keys a text field handles itself (Ctrl+Z/Y/A/X/C/V, word
  moves) stay the field's.
- Run (`index.js`): configuration type `visual-script` (`forFile` claims `*.pyflow`, so Shift+F10 on the tab,
  Ctrl+Shift+F10, the run widget, Run › Run, Rerun, Stop and stdin work as for a script; the run plugin's
  `currentPyFile` accepts a viewer tab whose file another type's `forFile` claims). A script with problems is not run:
  the Run console lists them with their nodes and the canvas selects the first. Otherwise main writes the code to
  `<userData>/visual-script/<sha1 of the lower-cased path>/<name>_pyflow.py` (never named like a module, which Python
  would import instead of the real one; other .py files in that folder are removed) and runs it in the configuration's interpreter with the .pyflow's folder as working directory
  and on PYTHONPATH. Traceback links into the generated file open the .pyflow and select the node instead, and a
  failed run marks the innermost frame's node with the exception line (`markRuntimeError`).
- The tab's toolbar: Run (this script as its context configuration), Show Code (a read-only Monaco pane beside the
  canvas that recompiles as the graph changes; selected nodes highlight their lines, a click on a line selects its
  node; remembered in `visualScript.showCode`) and Export as Python… (`<name>.py` next to the script, or, when that name would hide a
  module the code imports, a standard module or an installed package (`VS.symbols.packages()`), a name the user picks
  in a dialog that suggests `<name>_script.py` and refuses a name that still hides a module; asks before
  overwriting with a Local History checkpoint, then opens it; also Find Action `VisualScript.ExportPython`).
  Project tree › New › Visual Script (after Python Package in file-templates' submenu) makes Start wired to Print
  "Hello" and opens it. The file icon is `nodeGraph` (`tools/file-icons/nodeGraph*.svg`).
- `tab.visualScript` (editor API): `graph()`, `selection()`, `select(ids)`, `centerOn(id)`, `fit()`, `view()`,

## Monaco 0.57 and IME input

PyIDE uses monaco-editor 0.57 (pinned exactly in package.json) through its AMD build in `min/vs`, loaded by `renderer/index.html` (`min/vs/loader.js`) and `renderer/core/ide.js`. Since 0.53 that build is made by Vite: `vs/editor/editor.main` appends its own `editor.main.css` and sets `self.MonacoEnvironment.getWorker`, which starts the editor, JSON, CSS, HTML and TypeScript workers from the hashed scripts in `min/vs/assets` (a blob worker that calls `importScripts` on their `file:` URL). PyIDE keeps that `getWorker` and does not define `MonacoEnvironment` itself. Monaco's message bundle for the UI language (`min/vs/nls/lang/ko.js`) is a plain script that sets globals, so `ide.js` adds it as a `<script>` before it requires `editor.main`. (Monaco's `vs/nls` loader plugin would `require()` it as an AMD module, which never resolves.) Internal AMD modules (`vs/...` other than `vs/editor/editor.main`) are no longer reachable. Inline completion providers must implement `disposeInlineCompletions` (it was `freeInlineCompletions`).

Editors take keyboard and IME input through the browser's EditContext API (`editContext`, on by default in Chromium). The focused element is `div.native-edit-context`, not a textarea (`textarea.ime-text-area` is only Monaco's IME helper). While a Korean syllable is being composed, Monaco draws it in the line itself, so the line keeps its syntax colors. Monaco 0.52 drew a textarea over the line in the plain foreground color until the syllable was committed. Dialogs treat `.native-edit-context` like a textarea: Enter there is a new line, and a dialog whose first field is an editor starts there.

The installer leaves out Monaco's `dev`, `esm` and its nested `node_modules`, the AMD worker copies in `min/vs/language/*/*.worker.js` (the `assets` copies are used), the message bundles other than Korean, and `dompurify` (bundled into the min build).

Test: `verify/ime-korean.mjs` (port 9170; in CI) on `verify/fixtures/ime-korean`. It drives IME compositions with CDP (`Input.imeSetComposition` per jamo, `Input.insertText` to commit) in the middle of a colored Python line. While a syllable is being composed, each token keeps its color, nothing is drawn over it and the syllable shows in the line. It also checks the committed text and caret, several syllables, Backspace inside a composition (a 229 "Process" key and a shorter composition), a cancelled composition, undo, a composition replacing a selection, and Korean in the find widget, a notebook cell and the Python Console input. Clips of the line before and while a syllable is being composed are saved to `verify/out/ime-korean/before.png` and `composing.png`.
